# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Maintaining this file

Capture only what reading the code won't tell you: cross-file architecture, the few non-obvious constraints, and project conventions. Do **not** restate things a single file or `grep` already reveals — crate `description` fields (see each `Cargo.toml`), API signatures, struct fields, doc-comment examples, generic `cargo` usage, or per-crate one-liners. Such content goes stale and bloats context. If a fact is verifiable by reading one file, leave it out.

## Orientation

reiny is a Rust SDK for distributed "grains" (processes) that communicate over [Zenoh](https://zenoh.io) pub/sub. Organizing principle: **type = topic**. A grain publishes and subscribes *by Rust type*, never by topic string — publishing `T` goes to `reiny/<domain>/<id>/T`, subscribing to `T` receives `reiny/<domain>/*/T` (the same type from every publisher; `<domain>` is a logical namespace from `--domain` / `REINY_DOMAIN`, default `"default"`). The type→topic mapping is generated at build time from a `Reiny.toml`, so user code only ever names types.

## Two build worlds — the root workspace excludes `examples/`

- **`crates/` is the core workspace.** Root `cargo build`/`test`/`clippy`/`fmt` operate here. Each crate's purpose is in its `Cargo.toml` `description`.
- **`examples/ping-pong-*` are each an independent cargo workspace** (own `Cargo.lock`), excluded from the root. To build or run one, `cd` into it. CI runs them as a matrix, excluding `ping-pong-cli` (shell-script walkthrough, no Rust).

## Build-time codegen pipeline (`reiny-build` + `reiny-macros` + `reiny`)

The cross-cutting flow to understand before touching any of these three:

1. Each grain's `build.rs` calls `reiny_build::compile()`.
2. `compile()` searches *upward* for the nearest `Reiny.toml` and resolves it in one of two layouts (`reiny_build::Mode`):
   - **per-project** (`[project]`): own `[publications]` + each `[dependencies]` project's public types → `publications::*` and `dependencies::<project>::*`.
   - **workspace** (`[internals]` / `[projects.*]`): the shared `[internals]` catalog → `internals::*`; the current package must appear as `[projects.<pkg-name>]`.
     - With an optional `[schema] crate = "<pkg>"`, workspace splits by the *current package*: the package whose name equals `[schema].crate` compiles `[internals]` **once** (full prost + `impl Topic`, exposed via `reiny::schema!()` in its `lib.rs`); every other package becomes a **consumer** that recompiles no protos and just re-exports `::<schema_crate>::internals::*` as `crate::internals`. This removes per-grain duplicate proto compilation. The shared `Topic`/`Message` impls live only in the schema crate (coherence makes them global). See `examples/ping-pong-schema`.
3. It compiles the protos with prost and writes `$OUT_DIR/reiny_generated.rs`: prost output under `__pb`, the re-export modules above, one `impl ::reiny::Topic` per type (where the topic string is embedded), and — if `[config]` is present — a typed `config::Config` plus a `cloudy.config()` extension trait.
4. `#[reiny::main]` `include!`s `reiny_generated.rs` into the crate root — which is why user code says `crate::publications::Ping`, not `reiny::...` — and wraps the async `main` in `reiny::__rt::run`.

Because the key is the Rust type, two crates sharing a type resolve to the same topic regardless of which "owns" it.

## `reiny-core` and `reiny-link` — reiny where zenoh does not run

- **`Topic` / `Descriptor` / `Service` live in `reiny-core` (`#![no_std]`)**; `reiny` re-exports them, so `reiny::Topic` is still the downstream path. The split exists only so an MCU can share type = topic. MCU crates alias it — `reiny = { package = "reiny-core" }` — which is why `reiny-build`'s generated `impl ::reiny::Topic` needs no `crate_path` option. `[config]` generation references `Cloudy`, so it cannot be used in such a crate.
- **`reiny-link` is sans-I/O.** `Link` never touches I/O or a clock: `feed` bytes in, `drain` (stream) / `drain_frame` (datagram) bytes out, `tick(now_ms)` for Ping / timeout / Hello re-send. The same `Link` runs on the MCU and on the host; `Host` (feature `std`) is just tokio driving it over a `Transport` (`Stream<T: AsyncRead + AsyncWrite>`, `Udp`, `transport::serial::open`). Wire: COBS + `[kind][fnv1a32(TYPE)][seq][payload][crc16]`; type *names* and `SCHEMA` fingerprints travel only in `Hello`, and fingerprint mismatch is decided once per connection, not per frame. Design + wire rationale: `docs/design/0.5.0.md` §3.
- Facts that bite: `Frame` is a `Copy` handle valid only until the next `next()` / `feed()` (generation-checked; stale reads return empty). Declarations (`publishes` / `subscribes` / `serves`) must precede the first I/O (`Error::Started`). `Reply` frames carry the *request* type's hash — decode them with `decode_reply::<S>`, not `decode::<S::Response>`. `Host::call` registers the pending reply under the same lock as the request so the driver cannot race it. `Udp::recv` swallows `ConnectionReset` (Windows reports a closed peer port via ICMP as a recv error).
- **Keep `link.rs` / `wire.rs` free of `std`** — CI builds `reiny-core` and `reiny-link` with `--no-default-features --target thumbv7em-none-eabihf`. std-only code goes under `#[cfg(feature = "std")]` (`host.rs`, `transport.rs`). `tokio-serial` is pulled with its default features off so no libudev is needed on Linux runners.
- **`LinkEngine` (feature `engine`, default) puts a `Cloudy` on a link, and it always runs the `Link` in bridge mode** (`Link::as_bridge()` → `HELLO_BRIDGE`): the engine never declares types, the peer treats it as subscribing / serving everything, and the peer's Hello *is* the presence (`@grain`, PUB tokens, SERVE `@service` tokens). Consequences: a `declare_alive` on the engine is local only (never reaches the peer); the peer must `calls::<S>()` (flag `CALLS`) for its requests to be routable by name; LATCHED types are cached in the engine to answer payload-less (latched) queries; a `LinkQuery` dropped unanswered sends `Error("no reply")` because links have no finalize. `Host::recv` is `&self` (tokio mutex) so the engine task and the caller share one `Arc<Host>`.

## `Engine` — `Cloudy` is engine-agnostic (0.5.0)

- **`Cloudy` holds `Arc<dyn engine::Engine>`**; the trait is the five primitives (`publisher` / `subscribe` / `declare_alive` + `alive` + `watch_alive` / `respond` + `query`) and nothing else. Everything above it — encode/decode, fingerprint check, latched ("presence, then query"), latest-wins, the Fifo/Ring receive buffers, service `Timeout` / `NoReply` — lives in `pubsub.rs` / `service.rs` and **must stay engine-neutral**. `engine/zenoh.rs` is the only place zenoh types appear besides `runtime.rs`'s config plumbing; `reiny-cli` still talks zenoh directly through `pub use zenoh` (it is not on the trait, deliberately — `docs/design/0.5.0.md` §7).
- **Contract facts that bite.** Engines call callbacks from their own non-async thread; reiny's callbacks only push into channels, and a full Fifo (256) blocks that thread exactly as zenoh's `FifoChannel` did. `Guard` drop = undeclare. Only `alive` and `RawReplies::next` are async — everything else is sync because zenoh 1.x builders' `.await` is `ready(wait())`, so `Publisher::send` / `Request::reply` are `async fn` in name only. `RawReplies::next` **must be cancel-safe** (it sits in a `select!` branch of `Subscriber::recv`). Timeouts belong to the engine (`QueryParams.timeout`); `Caller::call` still races its own timer against it (see Services).
- **`Key` is a struct**, rendered per engine. The zenoh rendering `reiny/<d>/<src>/<T>[/@chunk]` *is* the 0.4 wire. `source: None` / `ty: None` mean `*`; the grain token puts the verbatim `@grain` in the *type* slot (`Key::grain`), and `Key::matches` never lets a `*` type match a verbatim one — that is how `Key::all(d)` (`reiny/d/*/*`) and `Key::all(d).with_chunk("@service")` stay disjoint from grains. `source` is a filter, not necessarily part of the address (iceoryx2 puts it in a header).
- **`bridge::forward` loop rules** (`crates/reiny/src/bridge.rs`): (1) anything seen on side X from a source the bridge injected *into* X is an echo and is dropped (`Injected` counts tokens per source); (2) a relayed query always targets the exact `(source, type)` on the other side, never the incoming pattern — a `*` query on B hits one bridge responder per mirrored source, each forwarding to only that source on A, so A's bridge responders (which are for B-native sources) never see it. Subscriptions on a side are per type and exist only while a publisher token of that type is mirrored; a publisher / responder on the other side is created lazily per mirrored key. `Bridge` drop aborts both flow tasks, which drops every guard.
- `reiny bridge …` (`reiny-cli/src/bridgecmd.rs`) is the CLI's only tokio user (`Cloudy::open` / `Host` are async); it builds a runtime itself. `BusArgs::runtime_options(id)` is the shared path from fabric flags to `RuntimeOptions`. `reiny bridge iceoryx2` is behind the CLI feature `iceoryx2` (off by default — libclang).
- **`Local` has no locks**: one dispatcher thread owns all state and every operation is an `Op` through one unbounded channel, so ordering is total (declare-then-publish from one task is delivered in that order). A query finalizes when the last clone of its reply sender drops — i.e. when every matching responder replied or dropped its `LocalQuery`.
- **Feature `zenoh` (default)** gates `engine::Zenoh`, `pub use zenoh`, `ZenohSource`, `RuntimeOptions::{zenoh, zenoh_overrides, zenoh_config}`, `Cloudy::session()` (now `Option`) and the zenoh e2e modules. CI also runs `clippy` / `test -p reiny --no-default-features`; keep the no-zenoh build green.
- **Conformance** (`crates/reiny/src/engine/conformance.rs`) runs one `exercise(a, b)` against `Local` and `Zenoh` (loopback **37453**). It is `pub` behind reiny's `conformance` feature so engine crates run it from their own `tests/` (`reiny = { default-features = false, features = ["conformance"] }` as a dev-dependency); `e2e.rs` / `rpc_e2e.rs` stay as zenoh-specific regressions (wire, `@schema`, late links).

## `reiny-iceoryx2` — the engine whose shape is nothing like zenoh's

- **Not in `default-members`.** iceoryx2's `iceoryx2-pal-posix` runs bindgen on Windows / macOS (Linux binds libc), so a bare `cargo test` at the root skips this crate; CI uses `--workspace`, and locally it is `cargo test -p reiny-iceoryx2` with `LIBCLANG_PATH` pointing at a directory holding `libclang.dll` (the NuGet `libclang.runtime.win-x64` package is enough — no LLVM install needed). Without it the failure is a build-script panic in `iceoryx2-pal-posix`, not a reiny bug.
- **Rendering (design §5):** one pub-sub service per type `reiny/<d>/<T>` with a fixed `#[repr(C)]` user header `Meta` (key text ≤ 224 B, attachment ≤ 32 B, unix ns, flags); `source` is a filter applied in the engine thread, not part of the service name. One request-response service per type `reiny/<d>/<T>/q` carries latched, services and `@schema`: the query's *pattern* key rides in the request header and every server that does not match drops the `ActiveRequest` — that drop is what finalizes the query (`PendingResponse::is_connected()` goes false). Presence is a `reiny-alive/<key>` (`@` spelled `_at_`) pub-sub service held open by the `Guard`; `alive` = `Service::list` after `try_cleanup_dead_nodes`, `watch_alive` = the engine thread diffing that list every 200 ms (no push; conformance's 5 s patience covers it).
- **Service settings are fixed constants** (`PORTS`, `BUFFER`, `INITIAL_SLICE`, …): `open_or_create` fails on a mismatch, so QoS must never leak into service settings — `Reliability` goes to the *port* (`BackpressureStrategy::RetryUntilDelivered` / `DiscardData`). **Keep the limits small**: iceoryx2 preallocates a port's shared memory as the *product* of the limits (a client segment is `required_amount_of_chunks_per_client_data_segment(max_loaned_requests)` × slice size, which folds in `max_servers` and `max_active_requests_per_client`). With 64 ports / 16 requests / 4 KiB the first request-response client of a type took **63 s** to create on Windows; with 16 / 4 / 1 KiB it is ~0.3 s. If a limit must grow, measure port creation first.
- `Iceoryx2::with_config` runs `create_dir_all` on `config.global.root_path()` (`C:\Temp\iceoryx2\` on Windows, `/tmp/iceoryx2/` on Linux) because iceoryx2 does not create it and fails node creation with a bare `InternalError` when it is missing.
- **Threading:** `ipc_threadsafe::Service`, so publishers / clients send from the caller's thread; one engine thread owns a `WaitSet`, re-attaches every registered listener each iteration (guards borrow listeners, so per-iteration attach avoids lifetime fights), drains *all* subscribers / servers on every wake, and polls presence. `Node` sits behind a `Mutex` only for service creation.
- Every service name uses only `[A-Za-z0-9_/.-]`; whether iceoryx2 accepts `@` or `*` was never verified — keep it that way.

## Three manifest files (don't conflate)

- **`Cargo.toml`** — Rust build.
- **`Reiny.toml`** — reiny's manifest: identity, published/dependency types, optional `[schema] crate` (workspace shared-schema crate), `[config]` schema + defaults. Read at build time by `reiny-build` (schema: `crates/reiny-build/src/lib.rs`, `Manifest`).
- **launch config** (e.g. `ping-pong.toml`) — *deployment*: a `[grain]` table read by the launcher saying which grains to spawn together (`depends_on`, `on_exit`, etc.). Every key is an equal grain (no privileged component types); key = instance name = default bin name.

## The `reiny` CLI (`reiny-cli`) — one binary, several non-obvious behaviors

The `reiny` binary lives in **`reiny-cli`** (it depends on `reiny-launch` as a library; `reiny-launch` is now lib-only). Subcommands `new`/`init`/`add`/`check`/`build`/`run`/`compress`/`bag`/`topic`/`node`/`service`/`bridge` plus two non-subcommand entry paths handled *before* clap in `main`:

- **Backward-compat launch:** `reiny <launch>.toml` (bare positional) and `reiny --config <launch>.toml` both mean `reiny run`.
- **Renamed-launcher self mode:** if `argv[0]`'s basename isn't `reiny` (i.e. a `reiny compress --launcher <name>` artifact), it reads `<name>.toml` next to itself and launches with no args.

Facts that span files:
- `reiny check [path]` resolves the nearest `Reiny.toml` and prints its layout mode + type→topic table **without compiling protos**. It uses `reiny-build` with `default-features = false` (the `compile` feature, which pulls `prost-build`/`protoc`, is off), calling `reiny_build::describe()` (the catalog view, not package-bound — contrast `compile()`'s package-scoped `resolve_for`). Manifest validation (identifier checks, topic-collision) runs here too, so misconfig surfaces at `check` time, not just at build.
- `reiny build` is just `cargo build` in the cwd — codegen happens via the grain's `build.rs` (`reiny_build::compile()`), so the wrapper stays thin.
- `reiny new`/`init` scaffold **standalone** cargo projects (not workspace members); their `Cargo.toml` gets **path deps** to the reiny crates found by searching upward for `crates/reiny` + `crates/reiny-build` (so generated projects build inside this repo). `reiny add` only edits the target's `Reiny.toml` `[dependencies]` (textual insert, preserving comments) — never `src`.
- `reiny run` must find grain bins that may live in **separate `target/` dirs** (each scaffolded grain is its own project). It builds a search-dir list (`<launch>/<grain>/target/{debug,release}`, `<launch>/target/...`, the launcher's own dir) and hands it to `reiny_launch::run_launch_dirs` (the multi-dir generalization of `run_launch`).
- `reiny compress` bundles only what's needed (reachable grain bins + non-system `.so`s via `ldd` + launch config + the launcher itself) into one self-contained dir.
- **`reiny bag` (`bagcmd.rs`) records/replays the bus to MCAP.** The line it draws: reiny only writes what needs the reiny/zenoh vocabulary (key shape, domain, source, presence, latched, fingerprint, `@schema`); everything the `mcap` CLI already does — filter/merge/split/convert/`cat --json` — is delegated, deliberately. It's added to the `SUBCOMMANDS` array in `main.rs` too (or `reiny bag …` is eaten by the bare-positional "that's a launch config" path). It reuses `reiny`'s own `Cloudy` machinery through three seams: `RuntimeOptions::zenoh_config()` (public, so bag builds a session with the same `--connect`/`REINY_DOMAIN`/default resolution a grain gets), `Topic::DESCRIPTOR` + the publisher's `@schema` queryable, and `reiny-build`'s `descriptors` feature (`descriptor_subset`/`message_fingerprint`, no `protoc`). Design + the record-vs-mcap split: `docs/design/bag.md`. The bin-crate has no lib target, so its e2e (`tests/bag_e2e.rs`) spawns the built `reiny` binary via `CARGO_BIN_EXE_reiny` against a loopback grain session on **port 37448** (one past the reiny e2e's 37447 — don't collide them).
- **`reiny topic / node / service` (`topiccmd.rs` / `servicecmd.rs`) share the bus vocabulary with bag through `bus.rs`** (`BusArgs::open`, `KeyParts`, `alive_keys`, `collect_schemas[_all]`). Every new subcommand must also be added to `SUBCOMMANDS` in `main.rs`, or it is eaten by the bare-positional launch path. `topic echo` and `service call` are the **only** place `prost-reflect` lives (`codec.rs`, decoding the descriptor a grain serves at `@schema`); `reiny-build`'s `descriptors` feature stays prost-reflect-free. A service key serves **two** `@schema` entries (request + response), which is why `collect_schemas_all` returns a `Vec` per key and `collect_schemas` picks the one whose short name equals the key's type segment.
- **`Topic::DESCRIPTOR` (defaulted `None`, like `SCHEMA`) makes a running grain describe its own types on the bus.** A `Some` publisher answers a queryable at `<its key>/@schema/<message>` with the crate's `FileDescriptorSet` (`reiny-build` generates `REINY_DESCRIPTORS = include_bytes!(…/reiny_descriptors.bin)` and points each `impl Topic` at it; multi-crate `[schema]` parts each carry their own set, imports included). The `@schema` chunk is a zenoh **verbatim** segment (leading `@`) — it matches neither `*` nor `**`, which is exactly why `reiny bag record`'s `reiny/<domain>/*/*` capture and any `reiny/<domain>/**` subscriber never see it. `reiny` never interprets the descriptor bytes (it just serves/embeds them); all decoding lives in `reiny-build` behind `descriptors`, so tests can round-trip a bogus `b"…"` set.

## Services (0.4.0) — what is not obvious from one file

- **The request type is the address.** `serve::<Req>()` puts a queryable on the same key a publisher of `Req` would use (`reiny/<domain>/<id>/<Req>`); the presence token goes to `…/<Req>/@service` so `publishers::<Req>()` never lists servers. A latched publisher and a server of the **same type** in one grain coexist because they tell queries apart by **payload presence**: `declare_latch` ignores payload-carrying queries and `Server::recv` ignores payload-less ones. Removing either check silently breaks the other side (`rpc_e2e.rs` pins it).
- **`Caller::call` decides `Timeout` with its own `tokio::time::timeout`** and hands zenoh a deadline one second later. zenoh reports its own timeout as "no more replies", indistinguishable from `NoReply`; measuring elapsed time was tried and is flaky.
- **`[services]` impls are emitted only in the crate that generates the request type** (`service_impls` filters by `plan.entries`), so in a multi-crate `[schema]` the response type must be owned by the same part or one of its `depends` — `resolve_services` rejects the rest. Coherence would reject it later with a worse message.
- `Cloudy::new` is now fallible: it declares the `@grain` liveliness token and does a 300 ms liveliness `get` to warn about a duplicate id. The e2e helpers `.expect()` it.

## Conventions & gotchas

- **Comments and rustdoc are in Japanese.** Match that, and read them for design intent before changing behavior.
- **`reiny-build` validates identifiers up front.** `[dependencies]` keys, `[publications]`/`[internals]` aliases, and `[schema].crate` all become Rust identifiers in generated code, so a hyphen (or keyword) is rejected with an actionable error pointing at the section — instead of a downstream `rustc` syntax error in `reiny_generated.rs`. Topic-segment collisions (two distinct types mapping to the same type name) are likewise rejected (`validate_no_topic_collision`).
- **`REINY_VERBOSE=1`** (a build-time env var) makes `reiny_build::compile()` print the resolved mode, every type→topic, and the deduped proto set via `cargo:warning=` — handy when an ownership/dependency assignment isn't compiling the type you expect.
- **`reiny-build` is feature-split.** The default `compile` feature pulls `prost-build`/`protoc`; `default-features = false` leaves only manifest resolution + topic derivation (used by `reiny check`). Keep prost-touching code under `#[cfg(feature = "compile")]`.
- `protoc` is **vendored** via `protoc-bin-vendored` — a bare `cargo build` needs no system protoc.
- **`crates/reiny/src/e2e.rs` and `rpc_e2e.rs` are live-zenoh tests, not unit tests.** Each opens real sessions over a fixed loopback port (multicast off); they live in `src/` rather than `tests/` because they need the private `Cloudy::new` — adding a public constructor just to test would be the wrong trade. Fixed ports, one per test binary so they can run in parallel: **37447** `reiny/src/e2e.rs` (presence / latched / domain / `latest(n)` / cancel-safety), **37448** `reiny-cli/tests/bag_e2e.rs`, **37449** `reiny/src/rpc_e2e.rs` (services), **37450** `reiny-cli/tests/topic_e2e.rs` (topic / node / service CLI), **37451–37452** the late-link islands in `e2e.rs`, **37453** `reiny/src/engine/conformance.rs` (zenoh run). Take the next number for a new one; if one starts failing everywhere at once, suspect its port. The e2e patience (5 s) is not generous under a loaded machine — do not add sessions to a test binary casually, and **never wait for a link with a fixed sleep**: use `e2e::wait_peers(listening_session, n)` (polls `info().peers_zid()`), which is what turned the `rpc_e2e` "servers() is empty right after start" flake into a deterministic wait.
- **`Subscriber::recv` is documented cancel-safe** — a deadline is `tokio::time::timeout(d, sub.recv())`, there is no deadline API. Keep it that way: never hold a sample pulled from the channel across an `.await` inside `recv_envelope` / `Chan::recv_async`. `latest(n)` swaps the zenoh handler for a `RingChannel` behind the private `Chan` enum so `Subscriber<T>` stays non-generic (it appears in downstream struct fields).
- **zenoh is a public dependency** (`pub use zenoh` + `Cloudy::session()`). Bumping zenoh's major version is a reiny breaking change; say so in the CHANGELOG when it happens.
- **Do not import zenoh's `QoSBuilderTrait` / `SampleBuilderTrait`.** Those traits live behind zenoh's `internal` + `unstable` features, but zenoh's `#[internal_trait]` macro *also* emits every one of their methods as an inherent method — so `.priority()`, `.congestion_control()`, `.express()` and `.attachment()` are callable on stable zenoh with no features enabled. Reaching for the trait import is what makes them look unavailable.
- **Multi-crate schemas ride cargo's `links` metadata, not `Reiny.toml`.** A `[schema.<name>]` crate emits `cargo:proto_include=` / `cargo:proto_types=`; dependents read `DEP_<LINKS>_PROTO_INCLUDE` / `_PROTO_TYPES` and convert them to prost `extern_path` entries. That indirection is deliberate: `Reiny.toml` is not shipped inside a published crate, so a schema crate consumed from crates.io has no other way to say where its protos live. Consequences: every schema crate needs `links = "<package name>"` hand-written in `Cargo.toml`, and `depends` must be transitively closed with matching Cargo dep edges (cargo only gives `DEP_*` to direct dependents). `examples/ping-pong-schema-split` is the worked example and the CI coverage for this path.
- **`prost-build` generates code for imported files too** (it passes `--include_imports`), which is exactly why the extern plumbing above is needed — without it a shared leaf type is generated separately in every crate that imports it, and the two are different Rust types.
- CI gate (mirror locally before pushing): `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings`, `cargo build --all-targets`. Run a single crate/test with `cargo test -p <crate>` / `cargo test <name>`.
