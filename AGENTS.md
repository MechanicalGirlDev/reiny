# AGENTS.md

This file provides guidance to coding agents (Claude Code and others) when working with code in this repository. `CLAUDE.md` is just `@AGENTS.md`.

## Maintaining this file

Capture only what reading the code won't tell you: cross-file architecture, the few non-obvious constraints, and project conventions. Do **not** restate things a single file or `grep` already reveals — crate `description` fields (see each `Cargo.toml`), API signatures, struct fields, doc-comment examples, generic `cargo` usage, or per-crate one-liners. Such content goes stale and bloats context. If a fact is verifiable by reading one file, leave it out.

## Orientation

reiny is a Rust SDK for distributed "launches" (processes) that communicate over [Zenoh](https://zenoh.io) pub/sub. Payload types come from `schema.yaml`; communication authority comes from the resolved runtime composition in `main.yaml`. Applications open named ports with bound source identities and policies. A catalog alone never grants communication; `ModuleContext::open` requires resolved module bindings from `apply` / `run`.

## Two build worlds — the root workspace excludes `examples/`

- **`crates/` is the core workspace.** Root `cargo build`/`test`/`clippy`/`fmt` operate here. Each crate's purpose is in its `Cargo.toml` `description`.
- **`examples/ping-pong-*` are each an independent cargo workspace** (own `Cargo.lock`), excluded from the root. To build or run one, `cd` into it. CI runs them as a matrix, excluding `ping-pong-cli` (shell-script walkthrough, no Rust).

## Build-time codegen pipeline (`reiny-build` + `reiny-macros` + `reiny`)

The cross-cutting flow to understand before touching any of these three:

1. Each launch's `build.rs` calls `reiny_build::compile()`.
2. `compile()` searches *upward* for the nearest `schema.yaml` (`version: 3` plus a `schema` envelope), with no `main.yaml` fallback, and resolves it in one of two layouts (`reiny_build::Mode`):
   - **per-project** (`schema.project`): own `exported_types` + each `dependencies` project's public types → `exported_types::*` and `dependencies::<project>::*`.
   - **workspace** (`shared_types` / `projects`): the shared `shared_types` catalog → `shared_types::*`; the current package must appear as `projects.<pkg-name>`, whose deduplicated `types` list describes catalog usage, not endpoint roles.
     - Named parts under `schema.schema_crates.<name>` assign proto ownership to schema crates. Each schema crate compiles its part once and exposes it via `reiny::schema!()`; consumers re-export shared types instead of recompiling them. Even a single schema crate requires a named part. See `examples/ping-pong-schema`.
3. It compiles the protos with prost and writes `$OUT_DIR/reiny_generated.rs`: prost output under `__pb`, the re-export modules above, one `impl ::reiny::MessageType` per type (where the complete protobuf name and fingerprint are embedded), and — if `config` is present — a typed `config::Config` plus a `cloudy.config()` extension trait.
4. `#[reiny::main]` `include!`s `reiny_generated.rs` into the crate root — which is why user code says `crate::exported_types::Ping`, not `reiny::...` — and wraps the async `main` in `reiny::run_with`.

Sharing a Rust type makes schemas compatible; only runtime wiring connects endpoints.

## `reiny-core` and `reiny-link` — reiny where zenoh does not run

- **`MessageType` / `Descriptor` / `Service` live in `reiny-core` (`#![no_std]`)**; `reiny` re-exports them, so `reiny::MessageType` is still the downstream path. The split lets an MCU share schemas while keeping endpoint identity in its static port table. MCU crates alias it — `reiny = { package = "reiny-core" }` — which is why `reiny-build`'s generated `impl ::reiny::MessageType` needs no `crate_path` option. `config` generation references `ModuleContext`, so it cannot be used in such a crate.
- **`reiny-link` is sans-I/O.** `Link` never touches I/O or a clock: `feed` bytes in, `drain` (stream) / `drain_frame` (datagram) bytes out, `tick(now_ms)` for Ping / timeout / Hello re-send. Explicit static port tables remain separate from schema catalogs. Every epoch-2 frame carries `RY` magic, endpoint hash, sequence and CRC inside COBS. Endpoint hashes cover length-prefixed namespace/port pairs, not message types. Hello validates the complete named port/source/request/response table and fingerprint version before admitting a peer. Reply payloads retain the response fingerprint. Keep all validation and state bounded and allocation-free on the MCU; std Host handles I/O.
- Facts that bite: `Frame` is a `Copy` handle valid only until the next `next()` / `feed()` (generation-checked; stale reads return empty). Declarations (`publishes` / `subscribes` / `rpc_client` / `rpc_server`) must precede the first I/O (`Error::Started`). `Reply` frames carry the destination server's endpoint hash and the response fingerprint — decode them with `decode_reply::<S>`, not `decode::<S::Response>`. `Host::call` registers the pending reply under the same lock as the request so the driver cannot race it. `Udp::recv` swallows `ConnectionReset` (Windows reports a closed peer port via ICMP as a recv error).
- **Keep `link.rs` / `wire.rs` free of `std`** — CI builds `reiny-core` and `reiny-link` with `--no-default-features --target thumbv7em-none-eabihf`. std-only code goes under `#[cfg(feature = "std")]` (`host.rs`, `transport.rs`). `tokio-serial` is pulled with its default features off so no libudev is needed on Linux runners.
- **Link bridge mode is transport tooling, not an application grant.** The internal bridge uses `HELLO_BRIDGE` and mirrors the peer's Hello as presence (`@launch`, PUB, SUB and SERVE tokens). Static applications must declare their named ports, including client ports for routable requests. LATCHED types are cached to answer payload-less queries; a `LinkQuery` dropped unanswered sends `Error("no reply")` because links have no finalize. `Host::recv` is `&self` (tokio mutex), allowing shared transport ownership.

## `Engine` — `ModuleContext` is engine-agnostic (0.5.0)

- **`ModuleContext` holds `Arc<dyn engine::Engine>`**; the trait is the five primitives (`publisher` / `subscribe` / `declare_alive` + `alive` + `watch_alive` / `respond` + `query`) and nothing else. Everything above it — encode/decode, fingerprint check, latched ("presence, then query"), latest-wins, the Fifo/Ring receive buffers, service `Timeout` / `NoReply` — lives in `pubsub.rs` / `service.rs` and **must stay engine-neutral**. `engine/zenoh.rs` is the only place zenoh types appear besides `runtime.rs`'s config plumbing; `reiny-cli` still talks zenoh directly through `pub use zenoh` (it is not on the trait, deliberately — `docs/design/0.5.0.md` §7).
- **Contract facts that bite.** Engines call callbacks from their own non-async thread; reiny's callbacks only push into channels, and a full Fifo (256) blocks that thread exactly as zenoh's `FifoChannel` did. `Guard` drop = undeclare. Only `alive` and `RawReplies::next` are async — everything else is sync because zenoh 1.x builders' `.await` is `ready(wait())`, so `Publisher::send` / `Request::reply` are `async fn` in name only. `RawReplies::next` **must be cancel-safe** (it sits in a `select!` branch of `Subscriber::recv`). Timeouts belong to the engine (`QueryParams.timeout`); `RpcClient::call` still races its own timer against it (see Services).
- **Named addresses cross engines.** Key epoch 3 distinguishes output payload addresses (`@out/port/type`) from input presence (`@in/port/type/@sub`) and module control tokens. Wildcard discovery does not grant a port. SDK replay, provenance, RPC replies and descriptor queries preserve exact namespace/port pairs; iceoryx2 may share type services internally but filters the full named target. Never reconstruct a missing port from its payload type or substitute a reply key after parse failure.
- **Named bridge routes:** `bridge::forward(a, b, schemas)` requires complementary input/output contracts and compiled fingerprints, supplied by descriptors or peer Hello metadata. Streams use SDK named raw ports, preserving exact input sources and output identity/policy. RPC validates both fingerprints and rewrites replies to its declared output identity. Register the bridge before calling readiness. Only launch/readiness/stop control routes retain original sources; reflected control tokens are suppressed. A bridge input cannot consume its own output namespace.
- `reiny bridge …` (`reiny-cli/src/bridgecmd.rs`) and managed supervision use tokio. Bridges use the explicit transport-tooling capability rather than opening an unbound application `ModuleContext`. `reiny bridge iceoryx2` is behind the CLI feature `iceoryx2` (off by default — libclang).
- **`Local` has no locks**: one dispatcher thread owns all state and every operation is an `Op` through one unbounded channel, so ordering is total (declare-then-publish from one task is delivered in that order). A query finalizes when the last clone of its reply sender drops — i.e. when every matching responder replied or dropped its `LocalQuery`.
- **Feature `zenoh` (default)** gates the Zenoh transport and its configuration. Application `ModuleContext` handles expose neither engines nor sessions; transport tools are a separate capability boundary. CI also runs `clippy` / `test -p reiny --no-default-features`; keep the no-zenoh build green.
- **Conformance** (`crates/reiny/src/engine/conformance.rs`) runs one `exercise(a, b)` against `Local` and `Zenoh` (loopback **37453**). It is `pub` behind reiny's `conformance` feature so engine crates run it from their own `tests/` (`reiny = { default-features = false, features = ["conformance"] }` as a dev-dependency); `e2e.rs` / `rpc_e2e.rs` stay as zenoh-specific regressions (wire, `@schema`, late links).

## `reiny-iceoryx2` — the engine whose shape is nothing like zenoh's

- **Not in `default-members`.** iceoryx2's `iceoryx2-pal-posix` runs bindgen on Windows / macOS (Linux binds libc), so a bare `cargo test` at the root skips this crate; CI uses `--workspace`, and locally it is `cargo test -p reiny-iceoryx2` with `LIBCLANG_PATH` pointing at a directory holding `libclang.dll` (the NuGet `libclang.runtime.win-x64` package is enough — no LLVM install needed). Without it the failure is a build-script panic in `iceoryx2-pal-posix`, not a reiny bug.
- **Rendering (design §5):** one pub-sub service per type `reiny/<d>/<T>` with a fixed `#[repr(C)]` user header `Meta` (key text ≤ 224 B, attachment ≤ 32 B, unix ns, flags); `source` is a filter applied in the engine thread, not part of the service name. One request-response service per type `reiny/<d>/<T>/q` carries latched, services and `@schema`: the query's *pattern* key rides in the request header and every server that does not match drops the `ActiveRequest` — that drop is what finalizes the query (`PendingResponse::is_connected()` goes false). Presence is a `reiny-alive/<key>` (`@` spelled `_at_`) pub-sub service held open by the `Guard`; `alive` = `Service::list` after `try_cleanup_dead_nodes`, `watch_alive` = the engine thread diffing that list every 200 ms (no push; conformance's 5 s patience covers it).
- **Service settings are fixed constants** (`PORTS`, `BUFFER`, `INITIAL_SLICE`, …): `open_or_create` fails on a mismatch, so QoS must never leak into service settings — `CongestionControl` goes to the *port* (`BackpressureStrategy::RetryUntilDelivered` / `DiscardData`); `BackendDefault` leaves its configured default intact. **Keep the limits small**: iceoryx2 preallocates a port's shared memory as the *product* of the limits (a client segment is `required_amount_of_chunks_per_client_data_segment(max_loaned_requests)` × slice size, which folds in `max_servers` and `max_active_requests_per_client`). With 64 ports / 16 requests / 4 KiB the first request-response client of a type took **63 s** to create on Windows; with 16 / 4 / 1 KiB it is ~0.3 s. If a limit must grow, measure port creation first.
- `Iceoryx2::with_config` runs `create_dir_all` on `config.global.root_path()` (`C:\Temp\iceoryx2\` on Windows, `/tmp/iceoryx2/` on Linux) because iceoryx2 does not create it and fails node creation with a bare `InternalError` when it is missing.
- **Threading:** `ipc_threadsafe::Service`, so publishers / clients send from the caller's thread; one engine thread owns a `WaitSet`, re-attaches every registered listener each iteration (guards borrow listeners, so per-iteration attach avoids lifetime fights), drains *all* subscribers / servers on every wake, and polls presence. The engine and worker share `Node` behind a `Mutex` for service creation and dead-node cleanup.
- Every service name uses only `[A-Za-z0-9_/.-]`; whether iceoryx2 accepts `@` or `*` was never verified — keep it that way.

## `reiny-ros2` — a bridge library, not an engine

- **Named routes, one ROS node.** ROS export/import and service routes open declared SDK ports and inherit their policies; they cannot select arbitrary Reiny sources by type. `Ros::new(&cloudy, name)` owns a `ros2_client::Context` + `Node` (behind a `std::sync::Mutex`, because every `Node::create_*` takes `&mut Node`) and spawns the node's `Spinner` on tokio. Route tasks are aborted on `Ros` drop. ROS message-type names remain explicit because a Rust type cannot tell you its `.msg` name.
- **`ros2-client` facts that bite:** `Context::new()` does *not* read `ROS_DOMAIN_ID` (reiny-ros2 does, plus `ROS_LOCALHOST_ONLY=1` → `DomainParticipantBuilder::with_only_networks([127.0.0.1])`); `Node::spinner()` panics if called twice; `Subscription` / `Server` futures need the message types to be `Sync`; a DDS request sent before the server is discovered is silently lost, so `import_service` wraps the call in a 10 s timeout and replies `reply_err` instead of hanging its route.
- **Windows debug builds abort inside rustdds** (mio 0.6 Windows UDP, null-pointer UB check in Rust 1.96): `tests/loopback.rs` is `#[ignore]` under `all(windows, debug_assertions)`; validate locally with `cargo test -p reiny-ros2 --release -- --include-ignored`. The test also avoids the machine's dead link-local adapters by building loopback-only participants.
- `export_auto` / `import_auto` go prost bytes → `prost_reflect::DynamicMessage` → serde (`use_proto_field_name`, i.e. snake_case) → ROS struct, and back; they require `MessageType::DESCRIPTOR` (hand-written `impl MessageType` types get an error, use the closure form).

## Build and runtime files (don't conflate)

- **`Cargo.toml`** - Rust build.
- **`main.yaml`** - runtime composition, normative guide `docs/modules.md`, field schema `docs/main.schema.yaml` (mirror of `reiny-launch/src/modules.rs`; update both together). Each runtime definition must have an executable `run` or nonempty `modules`. Schema catalogs are rejected.
- **`schema.yaml`** - build-time catalog discovered upward by `reiny-build`, with `version: 3` and a `schema` envelope. It can live beside a runtime manifest or in a schema-only package directory. Never derive runtime endpoint permissions from this file.

## Deployments (`reiny-launch` + `reiny-cli` + `reiny` managed mode)

- **Pipeline:** `modules.rs` resolves the tree into a `DeploymentPlan` (local sources caller-relative, Git sources through `acquire.rs` pinned in root `lock.yaml`, only `reiny update` moves pins) -> `artifacts.rs` runs declared Cargo builds and stages files -> `prepared.rs` freezes the result -> the hidden `__supervise` owner (`modulecmd.rs`) runs `deployment.rs`. `plan` must never build; Git fetch must never build; there is no fallback to a newer ref or a stale executable.
- **Contract boundary:** the owner passes `--module-bindings <abs json>` and `REINY_MODULE_REPORT` to each child; optional core bindings remain no_std-compatible. Manifests, catalogs, static declarations, resolved bindings and compiled reports have independent version-3 boundaries. Reports carry fingerprint version 2, endpoint namespace and tagged exact input sources/output identity. The owner resolves source.outputs[source.port], never searches by type. Deployment status version 2 embeds the new reports; authenticated control remains independently version 1.
- **App ownership and delegation:** v3 definitions own endpoint policies; calls supply connections and instance settings, not replacement contracts. An owned child has a distinct runtime/readiness namespace but publishes and serves under its host's endpoint namespace. The SDK aggregates its exclusive compiled port subset into the host report before host readiness. Every SDK context requires resolved bindings, including contexts opened on a reused engine.
- **Owner facts that bite:** one owner per deployment namespace, controlled only through the authenticated local `.reiny/control.json`; `status` reads the live owner and may return retained state with `owner_alive: false`; an unchanged module fingerprint keeps its pid on re-apply; `stop` is cooperative `@stop` (ack = request received) then reap, then owned-tree kill. Foreground `run` registers its stop subscription before installing Ctrl+C.
- Providers are a closed enum (`process`, `artifact`). Don't document or imply external provider plugins.
- `LinkEngine` preserves Data/Request/Reply fingerprints and supports bound SDK contexts. MCU applications still require their generated static Link port table. ID/key length caps fail, never truncate.
- `reiny bundle` keeps the invocation tree (no flattening) and a renamed launcher with a sibling `main.yaml` applies it with no args.
- Read-only discovery tools can inspect the bus. Data commands (`bag` record/play, topic receive/publish, service call, bridges) require explicit prepared endpoint contracts; they cannot infer authority from discovered types.

## Bus tools in `reiny-cli`

- `reiny new`/`init` scaffold executable modules with separate runtime `main.yaml` and build-time `schema.yaml`. Their `Cargo.toml` gets path deps to `crates/reiny` + `crates/reiny-build` found by searching upward, so generated modules build inside this repo. `reiny add` edits `schema.dependencies` in `schema.yaml`, never application behavior.
- `reiny check [path]` uses `reiny-build` with `default-features = false` (no `protoc`), so schema validation surfaces without compiling.
- **`reiny bag` (`bagcmd.rs`) records/replays the bus to MCAP.** The line it draws: reiny only writes what needs the reiny/zenoh vocabulary (key shape, domain, source, presence, latched, fingerprint, `@schema`); everything the `mcap` CLI already does — filter/merge/split/convert/`cat --json` — is delegated, deliberately. It reuses `reiny`'s own `ModuleContext` machinery through three seams: `RuntimeOptions::zenoh_config()` (public, so bag builds a session with the same `--connect`/`REINY_DOMAIN`/default resolution a launch gets), `MessageType::DESCRIPTOR` + the publisher's `@schema` queryable, and `reiny-build`'s `descriptors` feature (`descriptor_subset`/`message_fingerprint`, no `protoc`). Design + the record-vs-mcap split: `docs/design/bag.md`. The bin-crate has no lib target, so its e2e (`tests/bag_e2e.rs`) spawns the built `reiny` binary via `CARGO_BIN_EXE_reiny` against a loopback launch session on **port 37448** (one past the reiny e2e's 37447 — don't collide them).
- **`reiny topic / node / service` (`topiccmd.rs` / `servicecmd.rs`) share the bus vocabulary with bag through `bus.rs`** (`BusArgs::open`, `KeyParts`, `alive_keys`, `collect_schemas[_all]`). `topic echo` / `topic pub` and `service call` are the **only** place `prost-reflect` lives (`codec.rs`, decoding *and encoding* through the descriptor a launch serves at `@schema`); `reiny-build`'s `descriptors` feature stays prost-reflect-free. A service key serves **two** `@schema` entries (request + response), which is why `collect_schemas_all` returns a `Vec` per key and `collect_schemas` picks the one whose full protobuf name equals the key's type segment.
- **`MessageType::SCHEMA_FINGERPRINT` and `DESCRIPTOR` are explicit compiled contracts.** Fingerprints are mandatory; descriptors allow a running launch to describe its types on the bus. Publishers and subscribers with descriptors answer at `<their own key>/@schema/<message>` with their `FileDescriptorSet`, allowing CLI tools to encode for a launch that only listens. The `@schema` chunk is verbatim and invisible to ordinary data subscriptions. The SDK serves descriptor bytes; descriptor decoding remains in `reiny-build` behind `descriptors`.

## Services (0.4.0) — what is not obvious from one file

- **RPC and retention share query primitives, not endpoint authority.** Server addresses contain their declared output port and request type, with `@service` presence. Requests require payloads; retained-state queries require no payload. Keep these checks and exact port routing together so same-type servers and retained publishers stay independent (`rpc_e2e.rs` pins it).
- **`RpcClient::call` decides `Timeout` with its own `tokio::time::timeout`** and hands zenoh a deadline one second later. zenoh reports its own timeout as "no more replies", indistinguishable from `NoReply`; measuring elapsed time was tried and is flaky.
- **`services` impls are emitted only in the crate that generates the request type** (`service_impls` filters by `plan.entries`), so in a multi-crate schema the response type must be owned by the same part or one of its `depends_on` — `resolve_services` rejects the rest. Coherence would reject it later with a worse message.
- `ModuleContext::new` is now fallible: it declares the `@launch` liveliness token and does a 300 ms liveliness `get` to warn about a duplicate id. The e2e helpers `.expect()` it.

## Operations (0.5.0) — the launcher and the counters

Design record: `docs/design/operations.md` (its own judgement criterion, hence its own file even though it ships in 0.5.0). Four holes plugged with what reiny already had.

- **Historical:** 0.5 `depends` waiting belonged to the removed launch config. Managed readiness is now the explicit `@ready` (see Deployments).
- **`@launch` is transport presence, not readiness.** Deployment readiness requires every declared endpoint to be opened and an explicit `ready()` call. Startup synchronization must use the declared connections, not type-wide discovery.
- **Respawn backoff is a deadline, not a sleep.** 200 ms → ×2 → 30 s, reset once a child stayed up a minute (`next_backoff` is a pure function so it is testable). `pending` holds `(name, Instant)`; sleeping the backoff instead would make Ctrl+C take up to 30 s. The monitor loop therefore ends only when `children` **and** `pending` are both empty.
- **Subscriber presence is `reiny/v3/<domain>/<own namespace>/@in/<input port>/<T>/@sub`** — it identifies the receiver's declared input, independently of its exact output-source list. Unlike a publisher's token it is skipped (not refused) on an engine without liveliness: it changes nothing about how the subscription behaves. `LinkEngine` mirrors the peer's `flags::SUB` into the same facet.
- **The receive-buffer counters are the only signal there is.** `SubscriberStats { received, dropped, blocked }` plus a one-shot `warn!`; nothing goes on the bus and `reiny topic hz` does not show them (the CLI can only count *its own* buffer). The Fifo path still blocks exactly as before — `try_send` runs first purely so a full buffer can be counted, then falls through to the blocking `send`.
- **Bridge routes stay declared.** Neither `@sub` discovery nor peer Hello metadata creates a route; Hello supplies fingerprints, not endpoint authority.

## Conventions & gotchas

- **All in-code documentation is written in English** — comments, rustdoc, `//!` module docs, doc-test prose, and identifier-adjacent notes. This applies to new and edited code; older code still carries Japanese comments, so rewrite them in English when you touch that region rather than in a separate sweep. Read them for design intent before changing behavior. Chat replies and commit messages follow the user's language, not this rule.
- **`reiny-build` validates identifiers up front.** `dependencies` keys, `exported_types`/`shared_types` aliases, and `schema.schema_crates.<name>.crate` all become Rust identifiers in generated code, so a hyphen (or keyword) is rejected with an actionable error pointing at the section — instead of a downstream `rustc` syntax error in `reiny_generated.rs`. Protobuf packages remain part of the transport name; distinct packages may contain messages with the same short name.
- **`REINY_VERBOSE=1`** (a build-time env var) makes `reiny_build::compile()` print the resolved mode, every type→topic, and the deduped proto set via `cargo:warning=` — handy when an ownership/dependency assignment isn't compiling the type you expect.
- **`reiny-build` is feature-split.** The default `compile` feature pulls `prost-build`/`protoc`; `default-features = false` leaves only manifest resolution + topic derivation (used by `reiny check`). Keep prost-touching code under `#[cfg(feature = "compile")]`.
- `protoc` is **vendored** via `protoc-bin-vendored` — a bare `cargo build` needs no system protoc.
- **`crates/reiny/src/e2e.rs` and `rpc_e2e.rs` are live-zenoh tests, not unit tests.** Each opens real sessions over a fixed loopback port (multicast off); they live in `src/` rather than `tests/` because they need the private `ModuleContext::new` — adding a public constructor just to test would be the wrong trade. Fixed ports, one per test binary so they can run in parallel: **37447** `reiny/src/e2e.rs` (presence / latched / domain / `latest(n)` / cancel-safety), **37448** `reiny-cli/tests/bag_e2e.rs`, **37449** `reiny/src/rpc_e2e.rs` (services), **37450** `reiny-cli/tests/topic_e2e.rs` (topic / node / service CLI), **37451** the late-link hub in `e2e.rs` (37452 is free), **37453** `reiny/src/engine/conformance.rs` (zenoh run). Take the next number for a new one; if one starts failing everywhere at once, suspect its port. The e2e patience (5 s) is not generous under a loaded machine — do not add sessions to a test binary casually, and **never wait for a link with a fixed sleep**: use `e2e::wait_peers(listening_session, n)` (polls `info().peers_zid()`), which is what turned the `rpc_e2e` "servers() is empty right after start" flake into a deterministic wait. **Two loopback peers never find each other by gossip**: since zenoh 1.10 gossip advertises `get_locators_noloopback()`, so a third session bridging two `127.0.0.1` listeners links nothing. A late link has to be built the other way round — both sides `connect` to a hub that is opened later (`latched_survives_a_link_that_comes_up_late`).
- **`Subscriber::recv` is documented cancel-safe** — a deadline is `tokio::time::timeout(d, sub.recv())`, there is no deadline API. Keep it that way: never hold a sample pulled from the channel across an `.await` inside `recv_envelope` / `Chan::recv_async`. `latest(n)` swaps the zenoh handler for a `RingChannel` behind the private `Chan` enum so `Subscriber<T>` stays non-generic (it appears in downstream struct fields).
- **Application SDK communication stays named and bound.** Do not reintroduce type-only publishing/subscription/RPC, unbound contexts, or engine/session escape hatches when adding integrations.
- **Do not import zenoh's `QoSBuilderTrait` / `SampleBuilderTrait`.** Those traits live behind zenoh's `internal` + `unstable` features, but zenoh's `#[internal_trait]` macro *also* emits every one of their methods as an inherent method — so `.priority()`, `.congestion_control()`, `.express()` and `.attachment()` are callable on stable zenoh with no features enabled. Reaching for the trait import is what makes them look unavailable.
- **Multi-crate schemas ride cargo's `links` metadata, not catalog files.** A crate named under the catalog's `schema.schema_crates` map emits `cargo:proto_include=` / `cargo:proto_types=`; dependents read `DEP_<LINKS>_PROTO_INCLUDE` / `_PROTO_TYPES` and convert them to prost `extern_path` entries. This keeps schema dependencies usable from crates.io without the original `schema.yaml`. Every schema crate needs `links = "<package name>"` in `Cargo.toml`, and `depends_on` must be transitively closed with matching Cargo dep edges (cargo only gives `DEP_*` to direct dependents). `examples/ping-pong-schema-split` is the worked example and CI coverage.
- **`prost-build` generates code for imported files too** (it passes `--include_imports`), which is exactly why the extern plumbing above is needed — without it a shared leaf type is generated separately in every crate that imports it, and the two are different Rust types.
- CI gate (mirror locally before pushing): `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings`, `cargo build --all-targets`. Run a single crate/test with `cargo test -p <crate>` / `cargo test <name>`.
