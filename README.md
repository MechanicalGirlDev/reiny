# reiny

This project is reiny.
The way the data flows is just like rain.

reiny is a Rust SDK for distributed "launches" (processes) that communicate over
[Zenoh](https://zenoh.io) pub/sub. Applications communicate through **named ports**:
Rust types identify payload schemas, and runtime composition decides which
endpoints connect.

`reiny-build` compiles the catalog in `schema.yaml` from each launch's `build.rs`.
The separate `main.yaml` declares executable modules, endpoint policies, and
explicit wiring. A schema catalog generates types; it does not grant communication.
The deployment supplies the module bindings and logical domain.

```rust,ignore
use reiny::prelude::*;
use crate::exported_types::Ping;        // generated by reiny-build
use crate::dependencies::pong::Pong;  // ditto

#[reiny::main]
async fn main(cloudy: ModuleContext) -> reiny::Result<()> {
    let pings = cloudy.output::<Ping>("ping")?;
    let mut pongs = cloudy.input::<Pong>("pong")?;
    cloudy.ready()?;
    // ...
    Ok(())
}
```

Run the module through `reiny apply` or `reiny run`; `ModuleContext::open` requires
resolved `ModuleBindings`. See
[`docs/modules.md`](docs/modules.md).
Version 3 module definitions own endpoint policies and executable definitions;
project manifests reuse them through `source` and supply instance wiring and
configuration. The [0.9 migration guide](docs/design/0.9.0.md) covers instance
asset overrides; the [0.8 migration guide](docs/design/0.8.0.md) covers named
endpoint contracts.

Request/response uses named RPC endpoints with request and response schemas:

```rust,ignore
let mut adds = cloudy.rpc_server::<Add>("adder")?;
while let Some(req) = adds.recv().await {
    req.reply(Sum { sum: req.value.a + req.value.b }).await?;   // or req.reply_err("…")
}
let adder = cloudy.rpc_client::<Add>("adder")?;
let sum = adder.call(Add { a: 1, b: 2 }).await?; // Sum from the wired server
```

The application SDK exposes no engine or session escape hatch and no type-only
publish, subscribe, or RPC operations. Transport tooling stays separate from
the module communication contract.

## Crates

### Everyday Rust development

For a Rust launch, depend on `reiny` and add `reiny-build` under
`[build-dependencies]`. Install `reiny-cli` for the `reiny` command.

| Crate | Role |
| --- | --- |
| [`reiny`](crates/reiny) | The SDK itself: `ModuleContext` (the pub/sub handle) and the `#[reiny::main]` runtime |
| [`reiny-build`](crates/reiny-build) | `build.rs` helper: compiles protos from `schema.yaml` and generates payload types and fingerprints |
| [`reiny-cli`](crates/reiny-cli) | The `reiny` command: plan / apply / run / status / stop / update / bundle for deployments, scaffold (new/init/add), check, build, bag, topic / node / service introspection, `bridge serial\|udp\|iceoryx2` |

### Supporting libraries

These are normally used through the SDK or CLI. Depend on them directly when
sharing message types with MCU firmware or embedding the launcher.

| Crate | Role |
| --- | --- |
| [`reiny-core`](crates/reiny-core) | The type vocabulary (`MessageType` / `Service` / `Descriptor` / `Qos`), `no_std`; re-exported by `reiny`, used directly by MCU firmware |
| [`reiny-macros`](crates/reiny-macros) | The `#[reiny::main]` proc-macro (used via `reiny`) |
| [`reiny-launch`](crates/reiny-launch) | Deployment library: resolves `main.yaml` module trees, pins Git sources, prepares artifacts and supervises managed processes; can be embedded without the communication SDK |

### Optional integrations

Choose these for the transport, ecosystem, or language your application needs.

| Crate | Role |
| --- | --- |
| [`reiny-link`](crates/reiny-link) | Named static ports over byte transports: a `no_std` sans-I/O `Link`, serial / UDP transports, and a tokio `Host` |
| [`reiny-iceoryx2`](crates/reiny-iceoryx2) | `Engine` on iceoryx2 — launches on one host over shared memory (needs libclang to build on Windows / macOS) |
| [`reiny-ros2`](crates/reiny-ros2) | ROS 2 bridge library on pure-Rust DDS (`ros2-client`): typed `export` / `import` of topics and services from a bridge launch, no ROS install |
| [`reiny-ffi`](crates/reiny-ffi) | UniFFI SDK for Python, Kotlin, Swift, and Ruby; shared C ABI for C, C++, JavaScript, TypeScript, and C# |

### Building this repository

At the repository root, `cargo build`, `cargo test`, and `cargo clippy` select
`reiny`, `reiny-cli`, and `reiny-build`. Their required supporting libraries are
still built as dependencies, including `reiny-link` for the CLI's serial / UDP
bridge. ROS 2, FFI, and iceoryx2 are not part of this default selection.

Select an integration or supporting library explicitly with `-p`:

```sh
cargo build -p reiny-ros2
cargo build -p reiny-ffi --features bindgen
cargo build -p reiny-iceoryx2
cargo test -p reiny-launch
```

`cargo test` at the root runs only the selected packages' tests, not their
dependencies' own tests. Use `cargo test --workspace` for all ten crates; CI
uses `--workspace` for Clippy and tests as well. The iceoryx2 build requires
libclang on Windows / macOS. `cargo fmt --all --check` checks the entire workspace.

## Getting started

For non-Rust launches, see [the multilingual FFI SDK](crates/reiny-ffi).
It uses the same type names and Protobuf wire bytes as Rust launches.

Use the `reiny` CLI to scaffold a module and run a deployment. Runtime modules
have `main.yaml`; Rust payload catalogs live in `schema.yaml`. The wiring rules and lifecycle are described in
[`docs/modules.md`](docs/modules.md).

```sh
cargo install reiny-cli --version 0.11.0 --locked   # installs the `reiny` command
reiny new my-module
reiny check my-module      # validate and show the type → topic map (no build)

cd examples/ping-pong-relay
reiny plan                 # resolved modules and connections, nothing built
reiny apply --detach       # build, start, wait for readiness, then return
reiny status
reiny stop
```

Record and replay the bus, `ros2 bag`-style (format is [MCAP](https://mcap.dev),
so Foxglove and the `mcap` CLI read it directly):

Data commands require resolved `--module-bindings` from a runtime composition.
In these commands, `$BINDINGS` is that prepared contract path; its stream inputs
and outputs determine what can be recorded or replayed.

```sh
reiny bag record --module-bindings "$BINDINGS" --type RobotState --out walk.mcap
reiny bag info walk.mcap
reiny bag play walk.mcap --module-bindings "$BINDINGS" \
  --map 'reiny/v3/lab/robot/@out/state/RobotState=state' --rate 0.5 --loop
```

Repeat `--map recorded-key=output` for every selected recorded channel and
declared replay output. The exact recorded namespace and port are retained in
MCAP metadata; replay never chooses an output by protobuf type. Missing,
duplicate, ambiguous, and schema-incompatible mappings are rejected.

Design and the split of what reiny records vs. what the `mcap` CLI is left to do:
[`docs/design/bag.md`](docs/design/bag.md).

Look at a live bus, `ros2 topic / node / service`-style:

```sh
reiny node list                       # live launch ids
reiny topic list                      # type → publishers / subscribers / servers
reiny topic hz robot_state --module-bindings "$BINDINGS"
reiny topic echo robot_state --module-bindings "$BINDINGS" --count 3
reiny topic pub command '{"stop":{}}' --module-bindings "$BINDINGS"
reiny service call calibration '{"start":{}}' --module-bindings "$BINDINGS"
```

Here `robot_state`, `command`, and `calibration` are declared input, output,
and RPC input port names, not type-wide communication grants.

See [`examples/`](examples) for runnable demos (each is its own cargo workspace).
For larger workspaces, [`examples/ping-pong-schema`](examples/ping-pong-schema)
shows the `schema.schema_crates` shared-schema crate that compiles the message catalog once
instead of per launch, and
[`examples/ping-pong-schema-split`](examples/ping-pong-schema-split) splits that
catalog across several independently publishable schema crates without
generating shared leaf types twice.
[`examples/ping-pong-service`](examples/ping-pong-service) is the request/response
sample (`schema.services` in `schema.yaml`).
[`examples/owned-child`](examples/owned-child) demonstrates an app-owned helper
with delegated retained state and RPC endpoints, plus a wired verification task.

## In-process components

Deployments started by `reiny apply` or `reiny run` place every module in its
own managed process. `reiny::component::ComponentHost` is a separate, newer
option: it runs trusted Rust components as Tokio tasks inside one process,
sharing one explicit engine (usually a single `engine::Local`).

Try the two-component demo:

```sh
cargo run -p reiny --no-default-features --example component_host
```

The [example](crates/reiny/examples/component_host.rs) shows the whole contract:

- **Registered factories.** A `ComponentRegistry` is an explicit allowlist of
  `ComponentFactory` values keyed by id. Names never load code dynamically, and
  registering the same id twice fails with `DuplicateFactory`.
- **Distinct bindings.** Each `ComponentInstanceSpec` names a factory and
  carries its own resolved `ModuleBindings` and optional TOML config. Namespaces
  must be unique, and hosted instances must be top-level modules without
  children or executables. Components open only their declared named ports
  through `ComponentContext` (`input`, `output`, `rpc_client`, `rpc_server`).
  Having a matching Rust type doesn't grant a port: authority comes from the
  bindings alone.
- **Shared delivery.** On a shared `Local`, `send_shared` and
  `recv_shared_envelope` pass the same `Arc` between components, as described
  under [shared delivery](#shared-delivery-inside-one-process).

A `Component` has three hooks. `prepare` opens and keeps its endpoint handles;
it must not publish or spawn detached work. The host then validates that the
prepared reports form the declared closed graph and commits readiness before
any `run` starts. `run` is a service: returning before shutdown counts as a
failure (`UnexpectedExit`). `stop` receives a `StopReason` after the active
hook's future has been dropped, including after a partial prepare.

`ComponentHost::launch` checks static inputs synchronously and returns a
`HostHandle`. Use `wait_running()` to wait for admission (or get the startup
error), `status()` or `subscribe()` for per-group and per-component phases, and
`stop()` for the shared terminal `HostOutcome`. Dropping the handle also
requests shutdown. The first failure in any component cancels the whole group
and is kept as `primary`, with cleanup errors listed separately.
`startup_timeout` and `stop_timeout` each cover the whole group, not one
component.

Know the limits before relying on it:

- Shutdown is cooperative. Hooks must yield and tolerate cancellation. Nothing
  forcibly terminates a stuck task or blocking native code.
- `HostOutcome::Unresponsive` lists the instances that didn't join before the
  stop deadline. It means completion is unconfirmed, not that the code stopped.
- There's no isolation between components: they share the process, memory,
  and engine, and they're trusted code.
- Stopping withdraws readiness. It doesn't revoke endpoint handles a component
  leaked elsewhere.
- Readiness lost before activation prevents every run. A loss after that final
  check can race a peer's first poll; the host then fails and stops the group.
  It isn't a distributed readiness transaction.

Not implemented yet: mixing in-process and process placement in one
deployment, placement through `main.yaml` or the CLI, a general step scheduler,
a job protocol, and a cross-language host.

## Message type contract

### Shared delivery inside one process

Named typed ports on the same `engine::Local` can opt into shared ownership:

```rust,ignore
let value = std::sync::Arc::new(state);
output.send_shared(std::sync::Arc::clone(&value)).await?;
let envelope = input.recv_shared_envelope().await;
```

`recv_shared()` returns `Option<Arc<T>>`; `recv_shared_envelope()` returns
`Option<Envelope<Arc<T>>>`. For the exact same Rust type, live delivery and
retained replay share the published allocation without protobuf encoding or
decoding. Exact named bindings and schema fingerprints are still checked first.
Sharing a protobuf name or fingerprint alone does not imply Rust type identity.

This API requires an immutable protobuf value: the publisher, receivers, and
any other aliases must not modify it through interior mutability while a queued
or retained delivery can exist. `Arc<T>` does not enforce that condition.
Existing `send(T)` keeps its send-time serialized snapshot, including for types
with mutable aliases; existing `recv()` and `recv_envelope()` still return owned
decoded values without requiring `Clone`.

Raw receivers, bridges, owned receives, different Rust types, and byte-only
engines continue to use protobuf bytes. A shared publication encodes lazily at
most once, with the cache also used for replay. Byte copies, `Arc` bookkeeping,
metadata allocation, and the existing Local dispatcher queue remain: this is
not an unconditional zero-copy or bounded-memory transport claim. FIFO,
latest-ring, replay/rejoin, readiness, cancellation, and QoS behavior are
unchanged. Non-Local engines need no implementation changes.

Instrumented tests check actual protobuf encode/decode calls and allocation
identity. No throughput or latency benchmark has been run for this increment.

### Schema metadata

Generated message types declare their complete protobuf `TYPE_NAME`, a mandatory `SCHEMA_FINGERPRINT: u64` and explicitly provide
`DESCRIPTOR: Option<Descriptor>`. Type-only implementations are unsupported.
Typed pub/sub and RPC reject missing, malformed, or mismatched fingerprints.
Build-time catalogs require `version: 3` and named schema parts, including when
there is only one schema crate.
