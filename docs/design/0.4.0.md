# reiny 0.4.0 設計

対象: `reiny` / `reiny-build` / `reiny-cli`（`reiny-launch` / `reiny-macros` は触らない）。
起点: `9f783f8`（0.3.0）。行番号はすべてこのコミット時点のもの。
依存: zenoh 1.9.0（`Cargo.lock`。API はすべて 1.9.0 のソースで確認した）。

> **この文書の位置づけ** —— 0.3.0 を実利用しているダウンストリーム（HumanoidSystem、
> grain 3 本 + GUI プラグイン 3 本）で「ROS 2 なら 1 行で済むのに reiny では手書きしている」
> ものを棚卸しし、0.4.0 で何を足し**何を足さないか**を決めたもの。0.3.0 と同じく、
> 実装の手順書ではなく判断の記録である。

---

## 0. 方針

0.3.0 の判定基準はそのまま使う:

> **type = topic というモデルが原因で書けなくなっているか。**
> そうならば reiny の責任。そうでなければ「逃げ道」を 1 本開けて終わりにする。

ただし 0.4.0 はもう 1 つ判定を足す。0.3.0 §4 で「実消費者がまだ居ない」を理由に却下した
ものが、1 年で消費者を得たからである:

> **手書きの代替を 3 か所以上で書いているか。** 書いているなら `session()` は逃げ道として
> 機能していない —— 逃げ道は「1 か所で 20 行」までであって「3 か所で同じ 20 行」ではない。

| #   | 渋み                                       | 一次ソース（ダウンストリーム）                                                                  | 0.4.0                        | 判定理由                                                                 |
| --- | ------------------------------------------ | ----------------------------------------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------ |
| 1   | request/response が無い                    | `CalibrationCommand→CalibrationState` / `SimCommand→SimState` / `ImuCommand`（`hs-proto/proto/control.proto:142,214`, `sim.proto:10`） | **足す**（§2 Services）      | 3 か所が ack 無し・相関 id 無しの fire-and-forget で RPC を真似ている     |
| 2   | バスを覗く手段が GUI しか無い              | `reiny bag record` だけが raw 購読を持つ（`reiny-cli/src/bagcmd.rs:155`）                        | **足す**（§4 CLI）           | 行き止まり。`ros2 topic list / hz / echo` 相当がゼロ                     |
| 3   | 遅い購読者が zenoh のスレッドを止める      | zenoh `FifoChannel` の doc（`handlers/fifo.rs:28-33`）+ hs-gui が 100Hz `RobotState` を描画周期で消費 | **足す**（§3.1 `.latest(n)`） | type=topic の外の話だが、`session()` で書くと `Subscriber<T>` を捨てることになる |
| 4   | 「1 秒来なければ切断」を手書き             | `hs-gui/src/state.rs:341` `check_connection`                                                    | **足さない**（§3.2）         | `tokio::time::timeout` で足りる。reiny がやるのは cancel-safety の保証だけ |
| 5   | best-effort を指定できない                 | —                                                                                               | **足さない**（§3.3）         | zenoh 1.9 の `reliability()` は `unstable` かつ再送しない marker         |

**破壊的変更は無い。** キーの形（`reiny/<domain>/<id>/<TYPE>`）は 0.3.0 のままで、0.3 grain と
0.4 grain は同じ domain で通信できる。足すのは verbatim チャンク（`@grain` / `@service`）
だけで、これは 0.3.0 の `@schema` と同じく `*` / `**` のどちらにも見えない。

## 1. Services を type = topic に載せる方法

ROS 2 の service は **名前**でアドレスする（`/calibrate`）。reiny は型でアドレスするので、
service も型でアドレスする —— **request 型がサービスの住所**である:

```text
server : queryable  reiny/<domain>/<id>/<Req>      （+ liveliness token  reiny/<domain>/<id>/<Req>/@service）
client : get        reiny/<domain>/<id|*>/<Req>    payload = Req、応答 payload = Req::Response
```

publish と同じキー形なので、`from(id)` に相当する「宛先指定」も、presence に相当する
「誰が serve しているか」も、0.3.0 の仕組みがそのまま効く。

**なぜ request 型なのか（response 型や別名ではなく）。** クライアントが知っているのは
「何を頼むか」であって「何が返るか」ではない。`call::<Req>(req)` と書けば返り値の型は
`Req::Response` で決まる —— ROS 2 の `.srv` が request/response を 1 ファイルに束ねるのと
同じ束ね方を、Rust の関連型でやる。

**latched publisher との同居。** latched publisher（§0.3.0 §2.5）も同じキーに queryable を
立てる（`pubsub.rs:171-196`）。区別は **payload の有無**で付く: latched 購読者の `get` は
payload 無し（`pubsub.rs:287`）、service の呼び出しは必ず payload 有り。したがって

- service の queryable は `query.payload().is_none()` を無視する
- latched の queryable は `query.payload().is_some()` を無視する（**0.3.0 からの 1 行変更**、
  `declare_latch` の callback 冒頭）

この 2 行で「同じ型を latched publish しつつ serve する」grain も壊れない。
`Query::payload()` が `Option` なのは zenoh 1.9 で確認済み（`api/queryable.rs:253`）。

## 2. ランタイム（`reiny`）—— Services

### 2.1 trait

```rust
/// request 型がサービスの住所。`Topic::TYPE` がそのままキーの型セグメントになる。
pub trait Service: Topic + prost::Message + Default {
    type Response: Topic + prost::Message + Default;
}
```

`Response: Topic` を要求するのは `SCHEMA` 指紋を応答にも載せるため（§2.4）。生成型は
全部 `Topic` なので利用側に追加の負担は無い。手書き `impl Service` も 1 行で書ける ——
「第三者は自分の型に impl を書くだけで参加できる」という売りを service にも通す。

### 2.2 server 側

```rust
let mut srv = cloudy.serve::<CalibrationCommand>()?;      // Server<CalibrationCommand>
while let Some(req) = srv.recv().await {                     // Request<CalibrationCommand>
    let ack = handle(&req.value);
    req.reply(ack).await?;                                   // または req.reply_err("busy")
}
```

- `serve::<S>()` は queryable（`FifoChannelHandler<Query>`）+ liveliness token
  `<key>/@service` + `S::DESCRIPTOR` / `S::Response::DESCRIPTOR` があれば `@schema` queryable
  （§4.6 の `reiny service call` が request/response 両方の descriptor を要るため）。
- `Server::recv` は `Subscriber::recv` と同じ契約: シャットダウンで `None`、decode 不能は
  警告して読み飛ばす。**指紋不一致は読み飛ばさず `reply_err` する**（§2.4）。
- `Request<S>` は zenoh の `Query` を抱えた **消費型**（`reply` / `reply_err` が `self` を
  取る）。返さずに drop したら zenoh が query を finalize し、呼び出し側には応答ゼロが届く
  （= `CallError::NoReply`）。「返し忘れ」がハングではなく即エラーになるのは zenoh の
  finalize のおかげで、reiny が何かする必要は無い。
- `Request` に送信元 id は載せない。zenoh 1.9 の stable API に `Query` の送信元は無い
  （`zid()` は `unstable`）。要るなら request 型に自分で入れる。

### 2.3 client 側

```rust
// 1 発
let ack: CalibAck = cloudy.call::<CalibrationCommand>(cmd).await?;
// 宛先・タイムアウトを固定して使い回す
let calib = cloudy.caller::<CalibrationCommand>().to("hs-control").timeout(Duration::from_secs(2)).build();
let ack = calib.call(cmd).await?;
```

- `Caller<S>` は宣言を伴わない（zenoh の `get` は都度撃つ）ので `build()` は失敗しない。
  `call::<S>(req)` は `caller::<S>().build().call(req)` の糖衣。
- `to(id)` 無しは `reiny/<domain>/*/<Req>` へ撃ち、**最初の応答を採る**。server が 2 つ以上
  居る構成では `to()` で選ぶこと。`servers::<S>()`（§2.5）で列挙できる。
- zenoh の `get` builder に与えるもの: `.payload(req.encode_to_vec())`、
  `.attachment(S::SCHEMA)`、`.timeout(d)`（既定 10 s = zenoh の既定）、
  `.consolidation(ConsolidationMode::None)`。**consolidation を明示で切る**のは、
  service はキャッシュではなく、同じキーの 2 応答が「重複」ではなく「別の答え」だから。
  `accept_replies` は既定（`MatchingQuery`）のまま —— server は自分のキー
  `reiny/<domain>/<id>/<Req>` で返し、これは問い合わせキー `reiny/<domain>/*/<Req>` と
  交差する（`api/builders/query.rs:353` の既定）。

```rust
pub enum CallError {
    /// 応答が 1 つも来なかった: server 不在、または server が返さずに drop した。
    NoReply,
    /// タイムアウトまでに応答が無かった（`NoReply` と区別するのは経過時間で: >= timeout なら Timeout）。
    Timeout,
    /// server が `reply_err` した。中身は server が渡した文字列。
    Remote(String),
    /// 応答の指紋が `Response::SCHEMA` と違う。
    Schema { expected: u64, received: u64 },
    /// 応答が `Response` として decode できない。
    Decode(prost::DecodeError),
    /// zenoh 層のエラー。
    Zenoh(anyhow::Error),
}
```

`Remote` と `Schema` を `anyhow` に潰さないのは、呼び出し側が「server が居ない」と
「server が断った」を分岐したい場面（GUI のボタン活性など）が実際にあるから。

### 2.4 指紋

pub/sub と同じ規則を両方向に掛ける（`pubsub.rs:400-422` `schema_matches` を関数のまま
再利用する）:

- request: attachment に `S::SCHEMA`。server 側で不一致なら **`reply_err("schema fingerprint mismatch: …")`**。
  購読のように黙って捨てると、呼び出し側は `NoReply` を見て「server が居ない」と誤診する。
- response: attachment に `S::Response::SCHEMA`。client 側で不一致なら `CallError::Schema`。

### 2.5 presence

server の liveliness token は `reiny/<domain>/<id>/<Req>/@service` に置く。**publisher と同じ
キーに置かない**のは、`publishers::<Req>()` に server が混ざると `reiny topic list` で
`[pub]` と `[srv]` を区別できなくなるから。`@service` は verbatim チャンクなので
`reiny/<domain>/*/*` の liveliness get には見えず、`reiny/<domain>/*/*/@service` と
明示して撃った側だけが拾う（`@schema` と同じ性質、0.3.0 §8.1）。

```rust
cloudy.servers::<S>().await?        // Vec<String>  —— publishers() と同じ実装、キーが違うだけ
cloudy.watch_servers::<S>()?        // Presence<S>  —— watch_publishers() と同じ
```

### 2.6 Actions は足さない —— 規約だけ書く

校正（`CalibStart … CalibStop` + `CalibrationState` ストリーム）は ROS 2 で言えば action
である。だが action = **service（開始・取消）+ feedback topic + result** に分解でき、
reiny には 3 つとも既にある（service / pub-sub / latched）。API を 1 系統足す代わりに
docs に規約を 1 段落書く: 「開始は service、進捗は topic、取消は同じ service の別
oneof、結果は latched topic」。ダウンストリームの校正はこの形にそのまま落ちる。

## 3. 購読側 QoS

### 3.1 `.latest(n)` —— 遅い購読者が zenoh を止めないために（足す）

zenoh の既定ハンドラ `FifoChannel` は **満杯になると push 側（= zenoh の受信スレッド）が
ブロックする**（`handlers/fifo.rs:28-33` の doc に明記。容量は
`API_DATA_RECEPTION_CHANNEL_SIZE` = 256）。100Hz の `RobotState` を描画周期でしか読まない
GUI は 2.5 秒でここに達し、その grain の**全購読**が詰まる。これは type=topic の外の話だが、
`session()` で `RingChannel` を使うと `Subscriber<T>`（指紋照合・latched・shutdown 連動）を
丸ごと捨てて書き直すことになる —— 逃げ道が 20 行で済まない。

```rust
let mut states = cloudy.subscriber::<RobotState>().latest(1).build()?;
```

- `latest(n)` = zenoh `RingChannel::new(n)`（`handlers/ring.rs:31-32`: 満杯なら**最古を捨てる**）。
  未指定は従来どおり `FifoChannel`（既定 256、ブロック）。既定を変えないのは、コマンド系
  （`ControlCommand` / `SimCommand`）が黙って落ちる方が制御では危ないから。
- `Subscriber<T>` を handler でジェネリックにしない。内部で
  `enum Chan { Fifo(FifoChannelHandler<Sample>), Ring(RingChannelHandler<Sample>) }` を持ち、
  `recv_async` を両方に生やす。公開型の形を変えないため（`Subscriber<T>` はダウンストリームの
  構造体フィールドに現れている）。
- `RingChannelHandler::recv_async` は 1.9 で存在する（`handlers/ring.rs:118-135`）。

ROS 2 の `history: KEEP_LAST(n)` に相当する。`KEEP_ALL` は既定の Fifo がそれ。

### 3.2 deadline / recv timeout —— 足さない。cancel-safety を保証する

`hs-gui/src/state.rs:341` の `check_connection`（1 秒無音で切断表示）は

```rust
match tokio::time::timeout(Duration::from_secs(1), sub.recv()).await {
    Ok(Some(m)) => …,      // 受信
    Ok(None)    => break,  // シャットダウン
    Err(_)      => stale(),// 無音
}
```

で書ける。reiny が足す API は無い。**足すのは保証**で、`Subscriber::recv` /
`recv_envelope` が cancel-safe であることを doc に明記し、テストで固定する:

- Fifo: flume `recv_async` は cancel-safe（値を取り出す前に drop しても失わない）。
- Ring: `recv_async` は `pull()` → `not_empty.recv_async().await` のループで、await 地点に
  取り出し済みの値を抱えていない（`ring.rs:124-133`）。通知だけ消費して cancel されても値は
  リングに残り、次の `recv` が拾う。
- latched の応答チャネル（`recv_reply`）も同じ flume。

「publisher が居なくなった」は timeout ではなく `watch_publishers` の `Left` で取るのが
正しく、これは 0.3.0 で済んでいる。timeout が拾うのは「居るのに黙っている」だけになる。

### 3.3 reliability —— 足さない

zenoh 1.9 の `PublisherBuilder::reliability` は `#[zenoh_macros::unstable]` で、しかも
「再送は起きない、リンク選択の marker に過ぎない」と doc にある（`builders/publisher.rs:152-158`）。
unstable feature を開けてまで載せる価値が無い。stable に降りたら builder に 1 行足す。

## 4. 内省 CLI（`reiny topic` / `reiny node` / `reiny service`）

`ros2 topic list / hz / bw / echo`、`ros2 node list / info`、`ros2 service list / call` の
reiny 版。`reiny bag` と同じ線を引く: reiny が書くのは **reiny/zenoh の語彙が要る部分**
（キー形・presence・`@schema`・指紋）だけ。

### 4.1 grain 単位の presence（ランタイムに 1 行足す）

`reiny node list` は「publisher を 1 つも持たない grain」も出さなければ ROS 2 の
`node list` にならない。`Cloudy::new` で liveliness token を
`reiny/<domain>/<id>/@grain` に 1 本立てる。verbatim なので既存のどの購読・記録にも見えない。

副産物として **id 重複の検出**が手に入る: 起動時に `reiny/<domain>/<id>/@grain` を
liveliness get し、既に居れば `warn!`（error にはしない —— `bag play --as` のような
意図的な成り代わりがある）。0.3.0 では同 id の 2 プロセスが黙って同じキーを共有していた。

### 4.2 `reiny topic list`

```text
$ reiny topic list [--domain <d>]        # d = '*' で全 domain
TYPE                 PUB               SRV
RobotState           hs-control        -
CalibrationCommand   hs-gui            hs-control
```

liveliness get を 2 発（`reiny/<d>/*/*` と `reiny/<d>/*/*/@service`）撃って型ごとに畳む。
購読者は出さない —— zenoh の stable API に「誰が購読しているか」は無く、reiny も
subscriber に token を付けていない。付ければ取れるが、subscriber は publisher より桁で多く、
liveliness の負荷を購読 1 本ごとに払わせる理由が今は無い（§5）。

### 4.3 `reiny topic hz` / `bw`

```text
$ reiny topic hz RobotState [--from hs-control] [--window 10]
source        rate      min      max      std dev   window
hs-control    99.8 Hz   9.9 ms   10.3 ms  0.08 ms   998
```

raw 購読 1 本（`reiny/<d>/<id|*>/<TYPE>`、bag record と同じ。`bagcmd.rs:155`）を
**source ごと**に集計する。`*` で複数 publisher が混ざるので、合算ではなく行を分ける。
時刻は受信側の `Instant`（zenoh timestamping に依存しない —— 既定で off なので）。
`bw` は同じループで payload 長を足すだけ。統計は自前 20 行、外部 crate は入れない。

### 4.4 `reiny topic echo`

```text
$ reiny topic echo RobotState [--from id] [--once] [--raw]
```

bag record の `collect_schemas`（`bagcmd.rs:255-289`）と同じく `@schema` を 1 発撃って
descriptor set を取り、**`prost-reflect`** で `DynamicMessage::decode` → JSON に落とす。
bag §7 は「動的 decode は `mcap cat --json` がやる」として `prost-reflect` を CLI から
締め出したが、それはファイルの話で、**生きているバスに `mcap cat` は使えない**。ここが
`prost-reflect` を入れる唯一の場所になる。

- `DESCRIPTOR` を持たない型（手書き `impl Topic`）は decode できない。`--raw` と同じ
  hex ダンプに落とし、「publisher が `@schema` を名乗っていない」と 1 行添える。
- 指紋不一致は warn を出して**表示はする**（デバッグ用途で、落とす側の判断を隠すのは逆効果）。
- `prost-reflect` は reiny-cli の依存にだけ入れ、prost の版と揃える（prost 0.13 系。
  実装時に `cargo tree -i prost` で確定させる）。`reiny-build` の `descriptors` feature は
  従来どおり指紋・刈り込みのみで、prost-reflect には触らない。

### 4.5 `reiny node list` / `node info`

```text
$ reiny node list
hs-control  hs-gui  hs-physics
$ reiny node info hs-control
pub : RobotState WorldState ImuData WholeBodyCommand
srv : CalibrationCommand SimCommand
```

`list` は `reiny/<d>/*/@grain`、`info` は `reiny/<d>/<id>/*` + `reiny/<d>/<id>/*/@service` の
liveliness get。`node kill` は無い —— それはランチャの仕事で、grain には
`shutdown_now` しか無い（§5）。

### 4.6 `reiny service list` / `call`

```text
$ reiny service list
CalibrationCommand -> CalibAck     hs-control
$ reiny service call CalibrationCommand '{"start":{}}' [--to hs-control] [--timeout 2]
{"ok":true}
```

`list` は `@service` の liveliness get（応答型は `@schema` の 2 本目から取る）。`call` は
`@schema` で request/response の descriptor を取り、JSON → `DynamicMessage` → `encode` →
`get`（§2.3 と同じ builder）→ `DynamicMessage::decode` → JSON。これができると
**校正・物理リセット・IMU オフセットがシェルから撃てる**（GUI を上げずに実機を触る道）。

`reiny topic pub` は足さない: publisher が居ない型を流したい場面が典型で、そのとき
`@schema` を答える者が居ない（§5）。

### 4.7 置き場所

`reiny-cli/src/bus.rs` を新設し、bag と topic/node/service で共有する:
セッション構築（`RuntimeOptions::zenoh_config()` 経由、bag と同じ）、`KeyParts`
（`bagcmd.rs:739-766` から移す）、`collect_schemas`、動的 decode。`bagcmd.rs` は
差分で薄くなる。`main.rs` の `SUBCOMMANDS` 配列に `topic` / `node` / `service` を足す
（足し忘れると bare-positional の「launch config だ」経路に食われる —— CLAUDE.md 既述）。

## 5. 足さないもの（意識的に）

| 却下                                     | 理由                                                                                             |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `recv_timeout` / `.deadline()`           | `tokio::time::timeout` で 1 行。reiny がやるのは cancel-safety の保証（§3.2）                    |
| `.reliability(best_effort)`              | zenoh 1.9 では `unstable` かつ再送しない marker（§3.3）。stable 化を待つ                          |
| `.queue(n)`（Fifo 容量）                 | 実需要が無い。`latest(n)` が要る場面はすべて「最新だけ欲しい」                                    |
| Actions API                              | service + topic + latched の規約で表せる（§2.6）。API 1 系統分の面積が増えるだけ                 |
| request のストリーミング応答             | zenoh の get は複数応答を許すが、型付き API に出すと `call` の戻り値が `Stream` になり全員が払う |
| `Request` の送信元 id                    | zenoh stable に無い（`Query::zid` は unstable）。要るなら request 型に入れる                      |
| subscriber の presence / `topic info` の購読者欄 | 購読 1 本ごとに liveliness の負荷を払う理由がまだ無い（§4.2）                              |

## 6. `Reiny.toml`（`reiny-build`）—— `[services]`

```toml
# per-project でも workspace でも同じ節。キーは表示名、値はカタログ（[publications] / [internals]）の別名。
[services]
Calibrate = { request = "CalibrationCommand", response = "CalibAck" }
SimControl = { request = "SimCommand", response = "SimAck" }
```

- 生成: `impl ::reiny::Service for <ReqPath> { type Response = <RespPath>; }` を
  `impl Topic` の直後に出す（`reiny-build/src/lib.rs:1349-1376` のループの隣）。
  `[schema]` モードでは schema クレートにだけ出る（`Topic` と同じ、coherence の都合）。
- 検証（`reiny check` でも走る）: `request` / `response` がカタログに存在すること、
  同じ `request` 型が 2 つの service に現れないこと（Rust の関連型は 1 つしか持てない ——
  rustc の coherence エラーより先に、節を名指しして止める。0.2 の識別子検証と同じ流儀）。
- `reiny check` の出力に `services:` 表を足す（`checkcmd.rs`、`Resolution` に
  `services: Vec<ServiceInfo { name, request, response }>` を足す）。
- `REINY_VERBOSE=1` は services も印字する。

手書き `impl Service`（第三者型）はこの節を要らない。

### 11.2 設計から変えた点

- **`Timeout` は経過時間ではなく自分の timer で決める。** §2.3 の「`>= timeout` なら Timeout」は
  実機で外れた(zenoh の期限切れが自分の計測より僅かに早く見える)。`Caller::call` は
  `tokio::time::timeout(self.timeout, replies.recv_async())` で切り、zenoh 側の期限は +1 s
  後ろに置く。チャネルが閉じたら `NoReply`、timer が切れたら `Timeout` —— 決定的。
- **`Caller<S>` は `Session` のクローンを持つ**(`Cloudy` を借りない)。ダウンストリームが
  構造体フィールドに置けるようにするため。zenoh 1.9 の `Session` は `Clone`。
- **service のキーは `@schema` を 2 本名乗る**(request と response)。bag 由来の
  `collect_schemas` は 1 キー 1 descriptor を前提にしていたので、`collect_schemas_all`
  (`Vec` を返す)を足し、`collect_schemas` は「短い名前がキーの型セグメントに一致するもの」を
  選ぶ薄い層にした。`service list` の RESPONSE 列と `service call` の response decoder は
  ここから取る。
- **`topic echo` の出力は `<source>  <json>` 1 行 1 件**、`--count n` / `--duration s` /
  `--raw`(hex)。指紋の照合は「descriptor から算出した指紋 ≠ attachment」を送信元ごとに
  1 度 warn するだけで、表示は続ける(§4.4 どおり)。途中参加の publisher は初見のキーで
  `@schema` を撃ち直す。
- **`node list` は `@grain` と publisher / server のトークンの和**。0.3 の grain
  (`@grain` を持たない)も出るようにするため。`node info` はその旨を 1 行添える。
- **`[services]` の別名は `<dep>::<Alias>` も受ける**(per-project の依存型)。client 側の
  クレートは request 型を自分で prost コンパイルするので、`impl Service` も自分の側に要る。
- **多クレート `[schema]` では response の所有区画を検証する**(request 区画と同じか、その
  `depends` にあること)。impl は request 型を定義するクレートにしか置けないので、外せば
  rustc の coherence エラーになるが、節を名指しした方が早い。
- **`Cloudy::new` の id 重複チェックは 300 ms の liveliness get**(同期 `.wait()`)。起動時
  1 回だけで、セッションがまだ繋がっていなければ黙って通る(e2e がそれ)。
- **CHANGELOG の `!`**: 破壊的変更は無いので付けない(段 2 のコミットで一度付けて直した)。
