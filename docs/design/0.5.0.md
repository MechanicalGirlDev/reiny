# reiny 0.5.0 設計

対象: `reiny` / `reiny-build` / `reiny-cli` + 新クレート `reiny-core` / `reiny-link` / `reiny-iceoryx2` / `reiny-ros2`
（`reiny-launch` / `reiny-macros` は触らない）。
起点: 0.4.0（`9f783f8` 以降の main）。行番号はすべて 0.4.0 時点のもの。
依存: zenoh 1.9.0（`Cargo.lock`。1.10.0 が 2026-08-14 に出ている —— §2.3）、iceoryx2 0.9.3、
ros2-client 0.10.1（付録）。
改訂: 2026-08-29 —— iceoryx2 エンジン（§5）と ROS 2 bridge（§4）を 0.5.0 の範囲に**確定**（§9）。

> **この文書の位置づけ** —— 0.3.0 / 0.4.0 と同じく、実装の手順書ではなく判断の記録。
> 0.5.0 の主題は 1 つで、**reiny の芯から zenoh の形を抜く**こと。QoS・link・iceoryx2・ROS 2 は
> すべてその帰結として置く。

---

## 0. 方針

0.3.0 の判定基準（「type = topic が原因で書けないか」）と 0.4.0 の判定基準（「手書きの
代替を 3 か所以上で書いているか」）はそのまま使う。0.5.0 はもう 1 つ足す:

> **zenoh が走らない場所に grain を置きたいか。** 置きたいなら `session()` は逃げ道として
> 機能しない —— 逃げ道は「zenoh の先」にしか通じていない。

| #   | 要求                                     | 0.5.0                                   | 判定理由                                                                                                       |
| --- | ---------------------------------------- | --------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 1   | QoS を設定できるように                   | **足す**（§2）—— ただし reiny の語彙で  | 0.4 の builder は `zenoh::qos::Priority` を公開 API に晒している。エンジンを差し替えるなら語彙は reiny 側に要る |
| 2   | zenoh をトレイトで抽象化、別エンジンを挿す | **足す**（§1）—— `Cloudy` は具象のまま  | reiny が zenoh に頼っているのは 5 つの原始操作だけ（§1.1）。それ以外は既に reiny のコードで、動かさずに載せ替えられる |
| 3   | no_std の点対点エンジン（シリアルに限らない） | **足す**（§3）—— sans-I/O、実装は serial / UDP | MCU で zenoh は走らない（zenoh-pico は C）。「バイトを運べるものなら何でも」= I/O を持たない状態機械 + 運び手の trait |
| 4   | ROS 2 bridge                             | **足す**（§4、0.5.0 に確定）—— エンジンではなく bridge | ROS 2 は .msg で型付けされるので protobuf の生バイトを流しても RViz は読めない。型ごとの変換が要る = bridge      |
| 5   | iceoryx2 エンジン（2026-08-29 追加）      | **足す**（§5）—— `reiny-iceoryx2`       | 同一ホストのゼロコピー。それ以上に、5 操作の形が zenoh と**全部違う**本物のエンジンが 1 つ無いと trait は zenoh の写しになる（`Local` は zenoh の意味論をメモリで真似るだけ） |

**破壊的変更あり**（§8）。ただし **wire は変えない**: zenoh エンジンのキー形・attachment・
verbatim チャンクは 0.4 のままで、0.4 grain と 0.5 grain は同じ domain で通信できる。
壊れるのは Rust API の zenoh 露出部分だけ。

副産物として **grain のユニットテスト**が手に入る（§1.6 `Local` エンジン）。0.4 まで
`Cloudy` はネットワーク無しでは作れなかった。

## 1. エンジン抽象

### 1.1 reiny が zenoh に頼っている 5 つの原始操作

0.4.0 のコードを操作で数えると、zenoh に触っている箇所はこの 5 種に尽きる:

| 原始操作           | 使い所（0.4.0）                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------ |
| publish            | `PublisherBuilder::build` / `Publisher::send`（`pubsub.rs:92`）— key・bytes・attachment・QoS       |
| subscribe          | `SubscriberBuilder::build`（`pubsub.rs:305`）— pattern → sample 列。Fifo / Ring（`enum Chan`, `:358`） |
| liveliness         | `Cloudy::new`（`lib.rs:175` `@grain`）/ `alive_ids`（`:252`）/ `watch_key`（`:279`）/ publisher・server のトークン |
| queryable + get    | `declare_latch`（`pubsub.rs:180`）/ `declare_schema`（`:156`）/ `Server::declare`（`service.rs:70`）/ `Caller::call`（`:253`）/ latched の `get` |
| session config     | `ZenohSource` / `zenoh_config()` / `zenoh::open`（`runtime.rs:23, 157, 207`）                     |

それ以外 —— encode / decode、指紋の照合（`schema_matches`, `:525`）、latched の
「presence を見てから `get`」（`:288` のコメント）、latest-wins、`Shutdown` 連動、service の
`NoReply` / `Timeout` 判定 —— は **全部 reiny のコード**で zenoh の型を素通ししているだけ。
つまり抽象化の線は明確で、「5 操作を trait にし、上のロジックは動かさない」。

### 1.2 `Cloudy` は具象のまま —— `Arc<dyn Engine>`

```rust
pub struct Cloudy {
    engine: Arc<dyn Engine>,   // 0.4: session: zenoh::Session
    id: String, domain: String, shutdown: Shutdown, …
}
```

`Cloudy<E>` にしない。理由は 3 つ:

- `Cloudy` / `Publisher<T>` / `Subscriber<T>` はダウンストリームの**構造体フィールド**に
  現れている（0.4.0 §3.1 と同じ論点）。型引数が増えれば全部が書き換えになる。
- `#[reiny::main] async fn main(cloudy: Cloudy)` のシグネチャを変えない。
- bridge（§3.4 / §4）は **1 プロセスに 2 エンジン**を持つ。`dyn` なら `Cloudy::with_engine`
  で同じ id / domain / shutdown を共有する 2 本目が作れる。ジェネリクスだと型が 2 つ要る。

コスト: vtable 1 段 + `Pin<Box<dyn Future>>` の alloc が操作ごとに 1 回。ネットワーク往復の
前では測れない。ceiling は iceoryx2 のゼロコピー（§5.4）で、`Vec<u8>` を渡す API では
コピーが 1 回入る —— 0.5 の iceoryx2 はそのコピーを払う。loan API を trait に足すのは測って効いてから。

### 1.3 trait —— object-safe に絞る

```rust
pub type BoxFuture<'a, T> = Pin<Box<dyn Future<Output = T> + Send + 'a>>;
pub type Callback<T>      = Box<dyn FnMut(T) + Send>;
pub type Guard            = Box<dyn Any + Send + Sync>;   // drop = undeclare

pub struct Sample { pub key: Key, pub payload: Vec<u8>, pub attachment: Option<Vec<u8>>, pub timestamp: Option<u64> /* unix ns */ }
pub enum Presence { Joined(Key), Left(Key) }

pub trait Engine: Send + Sync + 'static {
    fn caps(&self) -> Caps;
    fn publisher(&self, key: &Key, qos: &Qos) -> Result<Box<dyn RawPublisher>>;
    fn subscribe(&self, key: &Key, on_sample: Callback<Sample>) -> Result<Guard>;
    fn declare_alive(&self, key: &Key) -> Result<Guard>;
    fn alive(&self, key: &Key) -> BoxFuture<'_, Result<Vec<Key>>>;
    fn watch_alive(&self, key: &Key, on_event: Callback<Presence>) -> Result<Guard>;   // 宣言済みは Joined で先に流す
    fn respond(&self, key: &Key, on_query: Callback<Box<dyn RawQuery>>) -> Result<Guard>;
    fn query(&self, key: &Key, req: QueryParams) -> BoxFuture<'_, Result<Box<dyn RawReplies>>>;
}
pub trait RawPublisher: Send + Sync { fn put(&self, payload: Vec<u8>, attachment: Option<Vec<u8>>) -> BoxFuture<'_, Result<()>>; }
pub trait RawQuery: Send { fn key(&self) -> &Key; fn payload(&self) -> Option<&[u8]>; fn attachment(&self) -> Option<&[u8]>;
    fn reply(self: Box<Self>, key: &Key, payload: Vec<u8>, attachment: Option<Vec<u8>>) -> BoxFuture<'static, Result<()>>;
    fn reply_err(self: Box<Self>, message: Vec<u8>) -> BoxFuture<'static, Result<()>>; }
pub trait RawReplies: Send { fn next(&mut self) -> BoxFuture<'_, Option<Result<Sample, Vec<u8>>>>; }   // None = 全 responder が finalize
```

- **キーは構造体**にする: `Key { domain, source: Option<String> /* None = * */, ty: Option<String>, chunk: Option<Chunk> }`。
  文字列の組み立て（`key_for`, `lib.rs:380`）と分解（`source_of`, `reiny-cli/src/bus.rs` の
  `KeyParts`）を各エンジンの描画に移す。zenoh は `reiny/<d>/<id>/<T>[/@chunk/…]` を描く。
  `reiny-link` は `ty` を 32 bit ハッシュにして `domain` を持たない（§3.2）。
- **受信バッファは reiny が持つ**。engine は sample ごとに callback を呼ぶだけ。Fifo（bounded
  256・満杯でブロック = zenoh `API_DATA_RECEPTION_CHANNEL_SIZE` と同じ）と Ring
  （`latest(n)`）を reiny 側で実装する（`enum Chan` の置き換え、60 行）。すべてのエンジンが
  `latest(n)` と cancel-safety（0.4.0 §3.2）を同じ実装で得る。契約: **engine は callback を
  非 async スレッドから呼ぶ**（zenoh がそう。`Local` は専用スレッドで呼ぶ）。
- **`caps()`** で無い機能を宣言する（`liveliness` / `query` / `attachment` / `wildcard_source`）。
  reiny は無い機能を **build 時にエラー**にする（`publisher::<T>().latched()` を query 無しの
  engine で → `Err("engine 'x' has no query support; latched needs it")`）。黙って劣化させない。
  唯一の例外は attachment: 無ければ指紋は `None` 扱いで素通し —— これは 0.3.0 §2.7 で
  既に決めた意味論（「照合できないときは通す」）そのもの。
- **`Key.source` は住所の一部とは限らない。** zenoh は `<id>` をキーに描くが、iceoryx2 は
  型 1 つ = service 1 つで source を header に載せる（§5.1）。engine の `subscribe` は
  `source: Some(id)` を **filter** として実装してよく、reiny 側はそれを前提にしない。
- **timestamp は `Option<u64>`**（unix ns）。`Envelope.timestamp` から `zenoh::time::Timestamp`
  が消える（`pubsub.rs:35`）。
- zenoh-only の逃げ道は残る: `cloudy.engine().downcast_ref::<Zenoh>()` → `Zenoh::session()`。
  `Cloudy::session()` は `#[cfg(feature = "zenoh")] fn session(&self) -> Option<&Session>` に
  なる（§8）。

### 1.4 クレート配置

```
reiny-core   (new, #![no_std])  Topic / Descriptor / Service（+ 0.5 で Qos）
reiny        (std)   Engine trait, Cloudy とその上の全ロジック, engine::zenoh (feature "zenoh", default), engine::Local, bridge
reiny-link   (new)   no_std sans-I/O Link + wire / feature "std": Transport(Stream / Udp / serial)+ Host。Engine 実装は段 2 の後
reiny-iceoryx2 (new) Engine 実装: iceoryx2 0.9（同一ホスト shm）。`reiny` を default-features = false で引く
reiny-ros2   (new)   bridge library (ros2-client)
```

- **`reiny-core` を切るのは no_std のため**だけ。MCU 側は `Topic` を知らなければ type = topic
  にならず、`reiny`（tokio / anyhow / toml）を no_std にするより trait 3 つを下に出す方が短い。
  `reiny` は `pub use reiny_core::{Topic, Descriptor, Service}` するので、ダウンストリームの
  パスは変わらない。`prost` は no_std でも alloc を要るので、`reiny-core` も alloc 前提。
- **zenoh エンジンは `reiny` の中に置く**（`reiny-zenoh` を切らない）。CLI も examples も
  zenoh 前提で、`reiny` = zenoh 入りが既定のままなら差分が最小。`default-features = false`
  で zenoh が抜け、`Engine` trait + `Local` だけになる —— 他エンジンのクレートはこれに依存する。
- **`reiny-build` は変えない。** 生成物は `impl ::reiny::Topic for …` を出す（`lib.rs:1425-1444`）
  ので、MCU 側は `Cargo.toml` で `reiny = { package = "reiny-core" }` と別名にすれば無改造で
  解決する。`[config]` 拡張（`:1510-`）は `Cloudy` を参照するので MCU では `[config]` を
  書かない（書けば rustc が止める）。別名が邪魔になったら `crate_path` オプションを足す。

### 1.5 起動

`RuntimeOptions` に `engine: Option<Arc<dyn Engine>>` を足す。`None` なら（feature `zenoh` で）
従来の `zenoh` / `zenoh_overrides` から開く。feature を切って `None` なら `run_with` が
`bail!("no engine")`。

`run_with` は **runtime + シグナル + `Cloudy::open(opts).await`** に割る。`Cloudy::open` は
async で tokio runtime を作らない —— `#[tokio::test]` の中で `Local` を挿して grain を
テストする入口であり、bridge が 2 本目を開く入口でもある。`#[reiny::main]` は変えない
（`engine = …` 属性は足さない。`run_with` を自前で呼ぶ 5 行で足り、それを 3 grain が
書いたら足す）。

`reiny-launch` は触らない。`--zenoh-config` を非 zenoh エンジンの grain に渡したら warn して無視。

### 1.6 `Local` エンジン（プロセス内バス）

`reiny::engine::Local`: `Arc<Mutex<State>>` 1 つに subscriptions / tokens / responders を
持つ、150〜200 行のバス。`Clone` して複数の `Cloudy::open` に渡せば同じバスに乗る。

役割は 2 つ。(1) **trait の適合テスト**（§10）の基準実装 —— 「`Engine` は実装できる」を
zenoh 抜きで示す。(2) ダウンストリームの **grain のユニットテスト**: ネットワーク・ポート・
zenoh 設定なしで `publish` → `subscribe` → `call` を回せる。これは 0.4 まで無かった。

wildcard / liveliness / query / attachment を全部持つ（`Caps` 全 true）。

### 1.7 raw bridge

`reiny::bridge::forward(a: &Cloudy, b: &Cloudy, filter)`: A の `reiny/<d>/*/*` を raw 購読して
B に**同じキー（source も同じ）で**流し、A の presence を B にトークンとして写す。逆方向も同じ
関数。ループ防止は「自分が B に宣言したトークンの source から B で受けた sample は、A の
エコーなので捨てる」の 1 規則。query（latched / service）は B の `respond` を A の `query` に
転送する。

エンジン trait が byte レベルなので、この bridge は**エンジンの組に依存しない** ~150 行で、
テストは `Local` ↔ `Local` で回る（ハードウェア不要）。0.5 の消費者は `reiny bridge serial|udp`
（§3.4）と `reiny bridge iceoryx2`（§5.6）—— 同じ関数に engine の組を変えて渡すだけ。
ROS 2 は型変換が要るので raw bridge には乗らない（§4）。

## 2. QoS —— reiny の語彙

### 2.1 型

```rust
// reiny-core
pub struct Qos {
    pub reliability: Reliability,   // BestEffort | Reliable        既定 Reliable
    pub priority:    Priority,      // RealTime | High | Normal | Low | Background   既定 Normal
    pub history:     History,       // KeepLast(n) | KeepAll         既定 KeepAll
    pub durability:  Durability,    // Volatile | TransientLocal     既定 Volatile
    pub express:     bool,          // 既定 false
}
impl Qos {
    pub const SENSOR:  Qos = …;   // BestEffort, KeepLast(1), Volatile        —— ROS 2 SensorDataQoS 相当
    pub const COMMAND: Qos = …;   // Reliable,   KeepAll,     Volatile        —— 既定
    pub const STATE:   Qos = …;   // Reliable,   KeepLast(1), TransientLocal  —— latched
}
```

ROS 2 / DDS の語彙を採るのは、ROS 2 bridge が QoS を**双方向に写す**必要があるから（§4.4）。
zenoh 固有の `CongestionControl` は公開 API から消し、`Priority` は reiny の enum になる。

### 2.2 builder

```rust
cloudy.publisher::<RobotState>().qos(Qos::STATE).build()?;
cloudy.publisher::<Imu>().reliability(Reliability::BestEffort).priority(Priority::High).build()?;   // 糖衣は残す
cloudy.subscriber::<RobotState>().latest(1).build()?;         // = history KeepLast(1)。0.4 のまま
cloudy.publisher::<Config>().latched().build()?;              // = durability TransientLocal。0.4 のまま
```

`.latched()` / `.latest(n)` / `.priority()` / `.express()` は残す。`.congestion()` は消える
（→ `.reliability()`）。publisher の `history: KeepLast(n > 1)` は 0.3 / 0.4 で却下した
「latched 履歴 n > 1」なので build 時にエラー（黙って 1 に丸めない）。

### 2.3 エンジンごとの写像

| Qos                       | zenoh                                                                     | link（§3）                         | ROS 2（§4）              | iceoryx2（§5.3）              | Local |
| ------------------------- | ------------------------------------------------------------------------- | ---------------------------------- | ------------------------ | ----------------------------- | ----- |
| reliability BestEffort    | `congestion_control(Drop)`                                                | 送信バッファ満杯で捨てる（`Full`） | BEST_EFFORT              | publisher `DiscardSample`     | 無視  |
| reliability Reliable      | `congestion_control(Block)`（既定）                                       | 満杯で `put` が `drain` を待つ     | RELIABLE                 | publisher `Block`             | 無視  |
| priority                  | `priority(RealTime/InteractiveHigh/Data/DataLow/Background)`              | 無視（1 本の直列リンク）           | 無視                     | 無視                          | 無視  |
| history KeepLast(n)（sub）| reiny の Ring（engine 非依存）                                             | 同左                               | KEEP_LAST(n)             | 同左                          | 同左  |
| durability TransientLocal | latched queryable（0.3 の実装そのまま）                                    | Hello 時に直近値を再送（§3.3）     | TRANSIENT_LOCAL          | query（zenoh と同じ経路）      | latch |
| express                   | `express(true)`                                                           | 無視                               | 無視                     | 無視                          | 無視  |

**zenoh の `reliability` は使わない。** 1.10.0 でも `unstable` かつ「再送は起きない、リンク
選択の marker」のまま（付録）。0.4.0 §3.3 の却下理由は生きている。一方で reiny の
`Reliability` は zenoh の **`congestion_control` に落とす** —— 輻輳で「捨てる」か「待つ」かは
実際に効く唯一のノブで、制御ループが欲しいのはこれ。「再送」の意味での reliability は
zenoh-ext の `AdvancedPublisher`（cache + recovery）が持つが、これも 1.10.0 で `unstable`。
stable に降りたら zenoh エンジンの `Reliable` をそちらに繋ぐ（trait も builder も変わらない）。

`Reiny.toml` / launch config への QoS 記述は **足さない**（0.3.0 §4・0.4.0 §5 と同じ判断:
配備の性質は builder に置く）。要るなら `[grain.<x>] qos = …` を launch 側で上書きする形に
なるが、実消費者が出てから。

## 3. `reiny-link` —— バイトを運べるものなら何でも

シリアル専用のエンジンは作らない。**「バイトを送れる者」を運び手（transport）として括り、
プロトコルは 1 つ**にする。運び手の最初の 2 つがシリアルと UDP。

### 3.1 形: sans-I/O

`Link` は **I/O も時計も持たない状態機械**。受け取ったバイトを `feed` で食わせ、送るべき
バイトを `drain`（stream）/ `drain_frame`（datagram）で吐き、`tick(now_ms)` で時を進める。
UART / USB CDC / RS-485 / DMA / 割り込み / embassy / RTIC / tokio —— どれに繋ぐかは
利用側の数行で決まり、**MCU でもホストでも同じ `Link`** を使う:

```rust
// MCU 側（#![no_std]、alloc あり）。バッファは所有でも借用でもよい。
let mut link = Link::<_, 8>::new("motor-board", [0u8; 512], [0u8; 512])?;   // 8 = 名乗る型の上限
link.publishes::<MotorState>()?;
link.subscribes::<MotorCommand>()?;
link.serves::<Calibrate>()?;

link.feed(&bytes_from_uart);                                       // Rx: どんな切れ方でもよい
while let n @ 1.. = link.drain(&mut out) { uart.write(&out[..n]); } // Tx
link.tick(millis());                                               // Ping / timeout / Hello 再送
link.send(&MotorState { .. })?;                                    // 相手が購読していなければ Ok(false)
while let Some(ev) = link.next() {
    match ev {
        Event::Data(f)    => if let Some(cmd) = link.decode::<MotorCommand>(&f) { … },
        Event::Request(f) => if let Some(req) = link.decode::<Calibrate>(&f) {
                                 link.reply::<Calibrate>(f.seq, &calibrate(req))?; },
        Event::Connected(_) => { /* latched な型はここで送り直す */ }
        _ => {}
    }
}
```

- `Frame` は **取っ手**（`Copy`）で、中身は `link.payload(&f)` / `link.decode::<T>(&f)` で読む。
  こうしないと「受けたフレームを見ながら `link.reply` する」が借用で書けない。取っ手は次の
  `next` / `feed` まで有効（世代番号で検出、古ければ空）。
- `Link` は **値を保持しない**（latched の再送も呼び出し側）。no_std で alloc-free に
  保つため。`Event::Connected` が再送の合図。
- `prost` は `default-features = false` で no_std だが **alloc は要る**（`Vec` / `String`
  フィールド）。MCU は `embedded-alloc` 等でヒープを持つこと。
  `// ponytail: alloc 必須。alloc-free は micropb + heapless に乗り換える段で trait を切る`

### 3.2 wire

```
COBS フレーム（0x00 区切り、再同期可）
  [kind u8][type_hash u32 LE][seq u8][payload …][crc16 LE]
kind: 0 Hello  1 Data  2 Request  3 Reply  4 Error  5 Ping
```

- **`type_hash` = FNV-1a 32 bit of `Topic::TYPE`**（`const fn`。コンパイル時に出る）。
  type = topic を 4 バイトで運ぶ。文字列はワイヤに載せない。
- **Hello** は起動時に双方が送り、受けた側は ack 付きで返す（ack には返さない）。中身は
  自分の id、名乗る型の `(hash, flags[pub|sub|serve|latched], SCHEMA u64)` の列と **型名**。
  型名を Hello にだけ載せるので、ホストはハッシュ → `TYPE` を設定なしで復元できる。
  ハッシュ衝突は宣言時（同じ `Link` 内）に `HashCollision` で止める。
- **指紋は Hello で 1 回照合**する（フレームごとに 8 バイト載せない）。不一致の型の Data は
  捨てて `Stats.dropped_schema` を数える（reiny 本体と同じ「照合できるときだけ落とす」）。
- **Ping** は無音時のみ（間隔と timeout は `LinkConfig` のノブ。物理層の遅延は板ごとに違う）。
  timeout = `Disconnected`。切れている間は同じ間隔で Hello を出し直す —— 相手が後から
  起動しても、ケーブルを抜き差ししても、どちらかの Hello が届いた時点で繋がる。
- `seq` は Request / Reply / Error の相関 id（255 in-flight）。Data では通し番号（欠落検出は
  呼び出し側に任せ、再送はしない —— Reliable は「満杯で `Full` を返し `drain` を待つ」まで）。
- **datagram でも同じ COBS 形**を使う。UDP なら 1 フレーム = 1 datagram で区切りは冗長だが、
  受信経路が `feed` 1 本で済む方が 1 バイトの節約より価値がある。
- CRC-16/KERMIT。`cobs` / `crc` crate（両方 no_std、依存 0）。

帯域の ceiling: 115200 baud ≈ 11 KB/s。40 バイトの状態量を 1 kHz なら 47 KB/s で足りない。
USB CDC（12 Mbps）か 921600 baud を推奨。reiny は圧縮しない。

### 3.3 ホスト側（feature `std`）: `Transport` と `Host`

```rust
pub trait Transport: Send {
    const DATAGRAM: bool;                                     // 境界を保つか(UDP)
    async fn send(&mut self, bytes: &[u8]) -> io::Result<()>;
    async fn recv(&mut self, buf: &mut [u8]) -> io::Result<usize>;
}
```

| 運び手                       | 実装                                                                                               |
| ---------------------------- | -------------------------------------------------------------------------------------------------- |
| `Stream<T>`                  | `T: AsyncRead + AsyncWrite` なら何でも。シリアル・TCP・pty・`tokio::io::duplex`（テスト）             |
| `transport::serial::open`    | `tokio-serial`（既定 feature 空 + `serialport` を `default-features = false` → libudev 不要）→ `Stream` |
| `Udp`                        | 相手は `with_peer` で固定するか最初の datagram の送り元で覚える。固定した相手以外は捨てる。Windows の WSAECONNRESET（相手ポート未開）は無視 |

`Host::spawn(link, transport)` が tokio task で `Link` を回す: 受信 → `feed` → `next`、
`send` / `call` / `reply` → `drain` → `transport.send`、100 ms ごとの `tick`。利用側は
`host.send(&T)` / `host.call::<S>(&req, timeout)` / `host.recv()`（`HostEvent`: Connected は
型名付き、Data / Request は bytes + `decode::<T>()`）。Reply / Error は `call` の待ち手が
消費する。`call` は request の積み込みと待ち手の登録を**同じ lock の中**でやる —— 間に
ドライバが送って応答まで受けると、登録前の応答が捨てられる。

### 3.4 `Cloudy` への接続（段 2 の後）

`Host` を `impl Engine`（§1.3）で包む: publisher = 相手が `sub` を名乗った型だけ送る、
subscribe = Data、liveliness = Hello / timeout、respond / query = Request / Reply。
`Caps.attachment = false`（指紋は Hello 経由）、`@schema` 無し（descriptor set はワイヤに
載せない）。それができると §1.7 の raw bridge で `reiny bridge serial /dev/ttyACM0` /
`reiny bridge udp 0.0.0.0:7000` が zenoh に繋ぎ、MCU は `reiny node list` / `topic hz` /
`bag record` にそのまま出る（`topic echo` は hex）。
`// ponytail: MCU 型の @schema は無し。要るなら bridge を MCU と同じ Reiny.toml の grain として書き、DESCRIPTOR を名乗らせる`

## 4. `reiny-ros2` —— bridge

### 4.1 経路の選択

| 経路                                    | 実装                                | ROS 2 インストール | 相手にできる RMW                                  | 判定                 |
| --------------------------------------- | ----------------------------------- | ------------------ | ------------------------------------------------- | -------------------- |
| **A. DDS を pure Rust で喋る**          | `ros2-client` 0.10.1（RustDDS）     | **不要**           | Fast DDS（Lyrical でも既定）/ Connext。Cyclone は未検証 | **採る**             |
| B. rmw_zenoh のキーを同じ zenoh session で喋る | 自前（RIHS01 型ハッシュ + rmw_zenoh のキー・liveliness 形式を再実装） | 不要 | rmw_zenoh のみ（Lyrical で Tier 1 だが既定ではない） | 保留。rmw_zenoh が既定になったら再考 |
| C. rcl に bind                          | `rclrs` 0.7 / `r2r`                 | **必要**（colcon） | 全部。params / actions も完全                     | この repo の CI で建たない。feature で後から足せる形にしておく |

A は `galactic` 〜 `lyrical` を feature で選べ（既定 `jazzy`）、`reiny-ros2` はそれを素通しする。

### 4.2 形: 型ごとの明示変換

エンジンではなく **ライブラリ**。利用側が bridge grain を書く:

```rust
#[reiny::main]
async fn main(cloudy: Cloudy) -> reiny::Result<()> {
    let ros = reiny_ros2::Ros::new(&cloudy, "reiny_bridge")?;                  // ROS_DOMAIN_ID は環境から
    ros.export::<RobotState, JointState>("/joint_states", Qos::SENSOR, |s| JointState { .. })?;   // reiny → ROS
    ros.import::<Twist, CmdVel>("/cmd_vel", Qos::COMMAND, |t| CmdVel { .. })?;                    // ROS → reiny（source = bridge の id）
    ros.export_service::<Calibrate, SetBool>("/calibrate", |req| .., |res| ..)?;
    cloudy.shutdown().await;
    Ok(())
}
```

- 変換はクロージャ。proto ↔ .msg の自動 codegen は**書かない**（フィールド名の対応規則を
  決めた瞬間に、その規則に合わない型のための逃げ道が要る —— 最初から逃げ道だけにする）。
- 同形の型には **opt-in の自動写像** `export_auto::<T, R>()`: `T::DESCRIPTOR` →
  `prost-reflect::DynamicMessage`（reiny 側は raw 購読で bytes を持っている）→ serde →
  `R: Deserialize`。フィールド名と型が揃っていれば 0 行。30 行で書ける（`prost-reflect` は
  `reiny-cli` が既に使っている版に揃える）。
- ROS の型は `ros2-client` の `Message`（serde 構造体）。標準 msg は
  `ros2-interfaces-jazzy`（feature ごとにパッケージ選択）を optional dep に置くが、必須に
  しない —— 自前の struct 3 行で足りる型が多い。
- ROS の domain（`ROS_DOMAIN_ID`）と reiny の domain は別物。bridge は両方を持つ。

### 4.3 presence

reiny 側: `import` は bridge の id を source に publish する（ROS の publisher に reiny の id は
無い）。`export` は reiny 側の presence に関係なく ROS publisher を立てる。ROS 側の graph
（discovery）は写さない。

### 4.4 QoS 写像

§2.3 の表の列。`ros2-client` の `QosPolicies` に reliability / history / durability を
1:1 で写す。`priority` / `express` は捨てる。逆向き（ROS → reiny）は import 時に指定した
`Qos` を reiny の publisher に使う。

### 4.5 検証は ROS 無しで回る

`ros2-client` は pure Rust なので、テストは **bridge と「ROS 役」の `ros2-client` node を同一
プロセスで RustDDS ループバック**に乗せればよい。ROS のインストールも docker も要らない。
`examples/ping-pong-ros2` を CI マトリクスに足す。

### 4.6 実装の形（0.5.0 で作る範囲、2026-08-29 確定）

| 部品 | 実装 |
| --- | --- |
| `Ros::new(&cloudy, node_name)` | `ros2_client::Context::new()` → `Node`（`NodeName` / `NodeOptions`）。`node.spinner()` を tokio task に spawn し、`cloudy.shutdown()` で abort。`ROS_DOMAIN_ID` は RustDDS が環境から読む |
| `export::<T, R>(topic, type_name, qos, f)` | `cloudy.subscriber::<T>()`（Fifo）→ `f(T) -> R` → `Publisher<R>::async_publish`。`R: ros2_client::Message`（serde）。`.msg` の型名は `R` から取れないので引数 `MessageTypeName::new("geometry_msgs", "Twist")` |
| `import::<R, T>(topic, type_name, qos, f)` | `Subscription<R>::async_stream()` → `f(R) -> T` → `cloudy.publisher::<T>().qos(qos)`。source は bridge の id（§4.3） |
| `export_service::<S, RS>(name, f_req, f_res)` | ROS `Server<RS>` → reiny `Caller<S>`: `async_receive_request` → `f_req` → `call` → `f_res` → `async_send_response`。`RS: ros2_client::Service` は `AService<Req, Res>` で 1 行、`ServiceMapping::Enhanced` |
| `import_service::<S, RS>` | 逆向き: reiny `Server<S>` → ROS `Client<RS>`（`async_send_request` → `async_receive_response`） |
| `export_auto` / `import_auto` | `T::DESCRIPTOR` → `prost_reflect::DynamicMessage` → `serde` → `R: DeserializeOwned`（逆も）。`reiny-cli` と同じ `prost-reflect` 版 |
| QoS | `QosPolicyBuilder`: reliability / durability / history を §2.3 の列で。`priority` / `express` は捨てる |
| 各 route | tokio task 1 本。変換失敗は `tracing::warn!` して続行（1 サンプルで bridge を落とさない）。`Ros` の drop で全 task abort |
| テスト | `tests/loopback.rs`: bridge + ROS 役 `Node` を同一プロセスで、`ROS_DOMAIN_ID` はテスト固有。CI runner に multicast が無い場合の逃げ道は要確認（付録） |

ROS 2 は `Engine` に依らない（`Cloudy` の上に載る）ので、段 2 と並行して書ける（§9）。

## 5. `reiny-iceoryx2` —— 同一ホストのゼロコピー、trait の 2 人目の他人

zenoh と `Local` だけで `Engine` を切ると、trait は zenoh の写しになる —— `Local` は zenoh の
意味論をメモリ上で真似るだけで、「違う形のエンジンでも成り立つか」を試していない。iceoryx2 は
5 操作の**形が全部違う**: wildcard が無い、liveliness が無い、query は request-response、
attachment は固定長の header。これが同じ適合テストを通れば、trait はエンジン非依存だと言える。
0.5 で作る理由の半分はそれで、残り半分が適所 —— 同一ホストで 1 kHz の制御ループと GUI /
logger を繋ぐとき、zenoh のループバック（TCP、encode → kernel → decode）より 1 桁速い。

### 5.1 描画 —— 型 = service、source は header

iceoryx2 に wildcard は無い。`reiny/<d>/*/<T>` を「publisher ごとの service を discovery で
追いかけて subscriber を増やす」で作ると presence と subscribe が絡んで 300 行になる。代わりに
**型 1 つ = service 1 つ**にし、source は header に載せる:

| reiny のキー | iceoryx2 |
| --- | --- |
| `reiny/<d>/<id>/<T>` へ publish | pub-sub service `reiny/<d>/<T>`（payload `[u8]` + user header §5.5）の publisher。header の `source = <id>` |
| `reiny/<d>/*/<T>` を subscribe | 同じ service に subscriber 1 本。`source: Some(id)` は header で **filter**（§1.3） |
| `reiny/<d>/<id>/<T>` の respond / query | request-response service `reiny/<d>/<T>/q`（`[u8]` ↔ `[u8]`）。request header に `target: Option<id>`、合わない server は `ActiveRequest` を即 drop（= finalize） |
| `declare_alive(key)` | pub-sub service `reiny-alive/<d>/<id>/<T>[/svc\|/grain]` を **`open_or_create` して握る**（port は作らない）。**存在 = 生存** |
| `alive(pattern)` / `watch_alive` | `Service::list` を 200 ms ごとに読み、前回との差分を Joined / Left に。読む前に `Node::try_cleanup_dead_nodes` |

- **1 型 = pub-sub + event + request-response の 3 service**。event は subscriber を起こすため
  （§5.2）。`// ponytail: 3 service/型。iceoryx2 が pub-sub に通知を内蔵したら 1 つに減らす`
- **service の設定は reiny が固定する**（`enable_safe_overflow(false)`、
  `subscriber_max_buffer_size(256)`、`history_size(0)`、`max_publishers` / `max_subscribers` 64）。
  `open_or_create` は設定が食い違うと失敗するので、**Qos を service に落としてはいけない** ——
  Qos は port に落とす（§5.3）。
- presence を「service の存在」で表すのは、port の表（`dynamic_config().list_publishers()`）が
  node id しか返さず、bridge が写す**他人の source**（§1.7）を表せないから。1 key = 1 service の
  コストは grain あたり shm セグメント 10〜20 個。
- 名前に `@` は使わない（使える文字を確かめていない —— 付録）。zenoh の verbatim チャンクに
  当たる隔離は接頭辞（`reiny-alive/`、`/q`）でやる。`reiny/<d>/**` に当たる raw 購読は
  「`Service::list` で `reiny/<d>/` 始まりの pub-sub service を集めて subscriber を増やす」で、
  bridge（§5.6）だけが使う。
- 死活: iceoryx2 は死んだ process の node を `Node::list` で `Dead` として見せ、
  `try_cleanup_dead_nodes` がその service を消す（他の node が握っていなければ）。engine thread が
  毎周期これをやるので、クラッシュした grain の Left は 400 ms 以内。zenoh の liveliness のような
  push は無い。

### 5.2 thread —— `ipc_threadsafe` + engine thread 1 本

```rust
pub struct Iceoryx2 {
    node: Node<ipc_threadsafe::Service>,
    state: Arc<Mutex<State>>,      // subscriptions / responders / watchers / alive tokens
    wake: Notifier,                // 自分の event service `reiny-wake/<pid>`
    thread: JoinHandle<()>,
}
```

- **`ipc_threadsafe::Service`** を使う。port が `Send + Sync` になる（内部 mutex 1 つの代価 ——
  1 kHz の前では測れない）。`RawPublisher::put` は呼び手のスレッドで直接 `loan_slice_uninit` →
  `write_from_slice` → `send` → `notifier.notify()` し、engine thread を経由しない。
  `RawQuery::reply` も同じ（`ActiveRequest` が `Send`）。
- **engine thread は受信専用**: `WaitSet` に全 subscriber / server の listener と `wake` の listener
  を attach。起きたら該当 port の `receive()` を空になるまで回して callback（§1.3 の契約「非
  async スレッドから呼ぶ」）。`attach_interval(200 ms)` で presence を読む。
- `subscribe` / `respond` / `watch_alive` は port を呼び手のスレッドで作って `State` に入れ、
  `wake.notify()`。engine thread が次に起きたとき WaitSet に attach する。`Guard` の drop は
  `State` から外して `wake.notify()`（WaitSet からの detach も engine thread）。
- `query`: 呼び手の async task が `client.loan_slice_uninit` → `send` → `PendingResponse`。
  `RawReplies::next` は `receive()` を 1 ms 間隔で poll し、`!is_connected()` かつ空で `None`
  （全 server が `ActiveRequest` を drop = finalize。§1.3 の契約と同じ）。
  `// ponytail: 1 ms poll。µs の call が要ったら RR の event listener を WaitSet に足して waker を起こす`

### 5.3 Qos

§2.3 の列。publisher の `BackpressureStrategy::{Block, DiscardSample}` が reiny の `Reliability`
に 1:1（`enable_safe_overflow(false)` だからこれが効く）。`Block` は同じ型の最も遅い subscriber
に合わせて publisher を止める —— zenoh の `Block` と同じ性質。`priority` / `express` は無視。
latched は zenoh と同じ query 経路（§5.1 の request-response）で、iceoryx2 の `history_size` は
使わない —— reiny の「presence を見てから get」を動かさないため。

### 5.4 ゼロコピーの ceiling

`RawPublisher::put(Vec<u8>)` は encode 済みの `Vec` を shm に 1 回 memcpy する（zenoh も同じ回数、
行き先が kernel なだけ）。受信は shm から `Vec` に 1 回コピーしてから callback —— shm の sample を
callback の外まで生かすと subscriber のバッファを食い潰すため。iceoryx2 の「本当のゼロコピー」は
publisher が shm に直接 encode し subscriber が shm から直接 decode すること。それには `Engine`
に loan API（`put_with(len, |buf| …)` と `Sample` の borrow）が要り、0.5 では足さない。数 KB ×
1 kHz ならコピー 2 回は 1 µs 級。測って効いてから（§7）。

### 5.5 payload と header

```rust
#[derive(Debug, ZeroCopySend)] #[repr(C)]
pub struct Header { source: [u8; 64], source_len: u8, attachment: [u8; 32], attachment_len: u8, unix_ns: u64 }
```

- payload は `[u8]` slice service。publisher は `initial_max_slice_len(4096)` +
  `AllocationStrategy::PowerOfTwo`（超えたら再確保。固定長にしない —— descriptor set のような
  数十 KB が稀に通る）。
- id は 63 バイトまで（publisher 作成時にエラー。黙って切らない）。attachment は 32 バイト
  （reiny が載せるのは 8 バイトの指紋。bridge が写すのも指紋だけ）。
- iceoryx2 の header に時刻は無い（付録）ので、`unix_ns` は送信側 engine が `SystemTime::now()`
  を入れる。`Sample.timestamp = Some(unix_ns)`。zenoh の HLC と違って時計合わせは無いが、同一
  ホストなので同じ時計。

### 5.6 zenoh との橋

iceoryx2 は同一ホスト限定。LAN の向こうの GUI / `reiny topic echo` / `reiny bag` から見えるように
するのは §1.7 の raw bridge で、`reiny bridge iceoryx2 [--domain d]` は「iceoryx2 の `Cloudy` と
zenoh の `Cloudy` を 1 プロセスに持って `forward` する」grain。CLI 自体は zenoh のまま（§7）、
ループ防止も §1.7 の 1 規則のまま。1 ホストに bridge は 1 本 —— id を `iceoryx2-bridge` に固定し、
2 本目は `Cloudy::new` の重複 id 警告で気付ける形にする。

### 5.7 起動と隔離

`Iceoryx2::new()` / `Iceoryx2::with_config(iceoryx2::config::Config)` → `Arc<Iceoryx2>` を
`RuntimeOptions.engine` に。node 名は `reiny/<pid>`（`Cloudy` の id は engine を作る時点では
未知。`iox2 node list` の見栄えだけの話）。テストは `config.global.prefix` をテストごとに変えて
shm を隔離し、1 プロセスに `Iceoryx2` を 2 つ（node 2 つ）作れば本物の IPC 経路が走る。
CI は ubuntu（Tier 2）。Windows も Tier 2 で開発機では動くが CI には足さない。feature は既定
（`std` + `console`）のまま。

### 5.8 クレート

`crates/reiny-iceoryx2`: `reiny = { default-features = false }` + `iceoryx2 = "0.9"`。`reiny` の
中に入れないのは zenoh を中に入れた理由の裏返し —— 既定の `reiny` を重くしない、Tier 2 の
プラットフォーム依存を既定に入れない。`Caps`: wildcard_source ○ / liveliness ○（poll）/
query ○ / attachment ○。

## 6. エンジン候補 —— 設計は受け、0.5 で作るのは 4 つ

trait の 5 操作（§1.1）をどう満たせるかで並べる。「作る」は 0.5.0 に入れるもの。

### 11.2 設計から変えた点

- **バッファは `B: AsRef<[u8]> + AsMut<[u8]>`** で、`[u8; N]`（所有）/ `&mut [u8]`（借用）/
  `Vec<u8>`（ホスト）のどれでも。設計の `&mut` 固定より MCU の書き方が 1 つ減る（static
  も lifetime も要らない）。
- **`Frame` は取っ手**（§3.1）。設計の `frame.decode::<T>()` は `link.decode::<T>(&f)` に
  なった —— フレームを見ながら `link.reply` するのに借用が通らないため。
- **`reply` は `Frame` ではなく `seq` を取る**。Reply が運ぶハッシュは request 型のものなので
  `reply::<S>(seq, &resp)` で足り、`Host` 側（`HostEvent::Request { seq, .. }`）と同じ形になる。
  同じ理由で Reply の decode は `decode_reply::<S>` に分けた（`decode::<S::Response>` は
  ハッシュが合わない）。
- **宣言は Hello の前に固定**（`Error::Started`）。宣言の後追いを許すと Hello を出し直す
  必要があり、相手の表の整合が崩れる。
- **`feed` は受け入れた長さを返す**。取り出し待ちのフレームで満杯のときだけ短くなる（`next`
  を回してから残りを渡す）。区切りが来る前に満杯なら捨てて次の区切りから再同期。
- **`drain_frame` は `out` に入らないフレームを捨てる**（詰まらせない）。`Link::MAX_ENCODED`
  以上の `out` を用意すれば起きない。
- **Hello の `SCHEMA` ビット**はワイヤ上の「`schema` 有効」の印で、表の `flags` からは外す。
- **`Udp` は Windows の WSAECONNRESET を無視**する（相手ポート未開を ICMP 経由で `recv` の
  エラーにされるため。相手がまだ起動していないだけ）。
- `embedded-io-async` adapter は**入れていない**（§7）。`impl Engine for Host` と
  `reiny bridge …` は段 2 の後。
- **publisher の既定 reliability が `Reliable` = `Block` になった。** §2.1 の既定どおりだが、
  0.4 は zenoh の既定（`Drop`）を素通ししていたので挙動変更 —— CHANGELOG に明記。戻すのは
  `Qos::SENSOR` か `.reliability(BestEffort)`。
- `type_hash` は `reiny-core` に置いていない（`reiny-link::wire` にあり、他に消費者が無い）。
  subscriber 側の `.qos()` も足していない（history 以外に意味が無く、`.latest(n)` で足りる）。
- **`Engine` は `alive` 以外すべて同期。** 設計 §1.3 は `put` / `reply` / `query` を `BoxFuture`
  にしていたが、zenoh 1.x の builder の `await` は `ready(wait())` と等価で、非同期にすると
  alloc が増えるだけ。本当に待つのは `RawReplies::next` だけ（cancel-safe 必須）。
  `Publisher::send` / `Request::reply` は API の形を保つため `async fn` のまま（await 地点なし）。
- **`Callback` は `Fn + Send + Sync`**（設計は `FnMut + Send`）。zenoh の callback がそれを
  要求し、reiny 側の callback はチャネルに積むだけなので `Fn` で足りる。mutex が 1 つ減る。
- **`Key.ty` は `Option`**。`reiny/<d>/*/*`（bridge の raw 購読）と chunk だけのキー
  （`@grain`）を同じ型で表すため。`source: None` = `*`。
- **`Cloudy::new` は async に**（重複 id の確認が `engine.alive` 経由になった）。e2e の
  helper も `.await`。
- **query の期限は engine に渡す**（`QueryParams.timeout`）。`Caller::call` は設計どおり自分の
  timer を先に切る。`Local` は `timeout_at` で列を閉じる。
- **`with_engine` / `bridge::forward` は段 5 へ。** 消費者（`reiny bridge`）が無い段階で書くと
  query 転送のループ防止（§1.7 の 1 規則は sample / presence にしか効かない）を決めずに
  済ませてしまう。
- `CallError::Zenoh` は `CallError::Engine` に。`Envelope.timestamp` は `Option<u64>`。

### 11.3 検証

- `cargo test -p reiny-core -p reiny-link`: wire 単体 6 + `Link` 11 + loopback 3（duplex /
  UDP / EOF）。`Qos` のプロファイルと zenoh 写像は単体 2 本。`Qos::STATE` = latched と
  `KeepLast(n > 1)` の拒否は `e2e.rs` の既存 latched テストに畳み込んだ（セッションを増やす
  と並行実行の e2e が負荷で flake する —— 5 s の patience は余裕ではない）。
- `engine/conformance.rs`: 1 本の `exercise` を `Local` と `Zenoh` に流す（grain presence /
  pub-sub と source / cancel-safety / `latest(2)` / presence の history と Left / latched /
  指紋 / service の往復・`reply_err`・`NoReply`・`Timeout`・居ない宛先 / shutdown）。

  を poll）に替えて 3 回連続で全通過。
- `cargo build -p reiny-core -p reiny-link --no-default-features --target thumbv7em-none-eabihf`
  が通る（`ci.yml` に追加）。
- `cargo clippy --all-targets -- -D warnings` / `cargo fmt --all --check` / `cargo test`
  がワークスペースで通る（`reiny` の re-export 化で既存 e2e は無改造）。
