# reiny 0.3.0 設計

対象: `reiny` / `reiny-build` / `reiny-macros` / `reiny-launch` / `reiny-cli`。
起点: `e66f30b`（0.2.0）。行番号はすべてこのコミット時点のもの。
依存: zenoh 1.10（`Cargo.lock` の解決は 1.9.0。API は 1.10 のソースで確認した）。

> **この文書の位置づけ** —— 0.2.0 を実利用しているダウンストリーム（HumanoidSystem、
> grain 3 本）で「reiny が原因で書けなかった」ものを棚卸しし、0.3.0 で何を足し
> **何を足さないか**を決めたもの。実装の手順書ではなく、判断の記録である。

---

## 0. 方針

reiny の価値は **343 行**（`crates/reiny/src/lib.rs` + `shutdown.rs`）という薄さにある。
機能を足して zenoh の劣化ラッパにするのが最悪手なので、判定基準を 1 つに固定する:

> **type = topic というモデルが原因で書けなくなっているか。**
> そうならば reiny の責任。そうでなければ「逃げ道」を 1 本開けて終わりにする。

この基準で 0.2.0 の渋みを仕分けた結果が下表である。

| #   | 渋み                               | 一次ソース                       | 0.3.0                        | 判定理由                                        |
| --- | ---------------------------------- | -------------------------------- | ---------------------------- | ----------------------------------------------- |
| 1   | zenoh セッション設定を渡せない     | `reiny/src/lib.rs:334`           | **足す**（起動オプション）   | 行き止まり。回避手段が存在しない                |
| 2   | `Cloudy.session` が private        | `reiny/src/lib.rs:86`            | **足す**（`session()`）      | 逃げ道。これ 1 本で #6 #8 #9 が自力解決になる   |
| 3   | publisher 指定購読・名前空間が無い | `reiny/src/lib.rs:110,128`       | **足す**（ns 段 + `from()`） | type=topic が直接の原因                         |
| 4   | `recv()` が送信元を捨てる          | `reiny/src/lib.rs:203`           | **足す**（`Envelope`）       | 同上。`Sample` はすでに手元にある               |
| 5   | 遅参者に何も届かない               | history/queryable 無し           | **足す**（latched）          | 同上。型しか無いので自前 topic で代替できない   |
| 6   | QoS を指定できない                 | `reiny/src/lib.rs:179-183,193`   | **最小限**（builder）        | `session()` でも書けるが 1 行が 20 行になる     |
| 7   | ランタイムがグローバルを奪う       | `reiny/src/lib.rs:304,327`       | **足す**（opt-out）          | 行き止まり（`try_init` の後勝ちは原理的に不可） |
| 8   | スキーマ版数が無い                 | `reiny/src/lib.rs:179-183`       | **足す**（指紋 attachment）  | 平坦な名前空間の副作用 ＝ reiny の責任          |
| 9   | reiny-build が prost を閉じている  | `reiny-build/src/lib.rs:557-568` | **足す**（本設計の目玉）     | 行き止まり                                      |

## 1. 破壊的変更は 1 つだけ —— キーに namespace 段を足す

```text
0.2.0:  publish  reiny/<id>/<TYPE>        subscribe  reiny/*/<TYPE>
0.3.0:  publish  reiny/<ns>/<id>/<TYPE>   subscribe  reiny/<ns>/*/<TYPE>
```

`<ns>` の既定は `"default"`。`--domain <ns>` / 環境変数 `REINY_DOMAIN` で切り替える。

**なぜキー段なのか。** zenoh 1.10 の `Config` / `Session` に namespace 相当は**存在しない**
（`zenoh/src/api/config.rs` と `session.rs` を grep して確認、該当ゼロ）。したがって
「同じ zenoh fabric 上での論理分離」はキーでやるしかない。

**何が解決するか。** 現状、同一マシン・同一 LAN で 2 系統を隔離する手段が無い。
ダウンストリームの運用ドキュメントには「別の launch が走っている間は 2 本目を上げるな
（勝手に相手を見つけて挙動が変わる）」という警告が実際に書かれている。ns 段はこれを消す。
実機とログ再生、ロボット 2 体、CI の並列ジョブが同じ理由で救われる。

ネットワークごと分けたい場合は §2.1 の zenoh config で別途できる。両者は目的が違う
（ns = 論理分離、zenoh config = 物理分離）ので、どちらも残す。

**互換性。** 0.2 grain と 0.3 grain は通信できない。0.x であり、既知の利用者は
「全 grain を同時に上げる 1 プロジェクト」なので、互換シムは作らない（維持費が上回る）。
CHANGELOG に BREAKING として明記する。

## 2. ランタイム（`reiny`）

### 2.1 セッション設定の口

```rust
pub enum ZenohSource {
    Default,                  // 既定（0.2 と同じ）
    Env,                      // zenoh::Config::from_env()
    File(PathBuf),            // zenoh::Config::from_file()
    Config(zenoh::Config),    // 呼び出し側が組み立てたもの
}

pub struct RuntimeOptions {
    pub id: Option<String>,
    pub domain: Option<String>,     // 既定 "default"
    pub zenoh: ZenohSource,         // 既定 Default
    pub install_tracing: bool,      // 既定 true（§2.6）
    pub log_level: tracing::Level,
    pub worker_threads: Option<usize>,
}

pub fn run_with<F, Fut>(opts: RuntimeOptions, user: F) -> Result<()>;
```

CLI 側に `--zenoh-config <path>` / `--domain <ns>` を追加し、頻出のものは短縮形として
`--connect <endpoint>` / `--zenoh-mode peer|client` も受ける（内部で `insert_json5`）。
`reiny-launch` の `GrainEntry`（`reiny-launch/src/config.rs:56`）に `domain` と
`zenoh_config` を足し、launch config から子へ渡せるようにする。

> **reiny 側で zenoh config の TOML スキーマは定義しない。** zenoh の JSON5 を
> そのまま渡すだけにする。ラップした瞬間に zenoh の設定項目を追随する義務が発生し、
> 「薄さが価値」という前提を裏切る。

### 2.2 逃げ道 —— `session()` を開ける

```rust
impl Cloudy {
    /// 内部の zenoh セッション。reiny が包んでいない機能（queryable / liveliness /
    /// attachment / スカウティング操作）へ直接届くための逃げ道。
    pub fn session(&self) -> &zenoh::Session;
}

pub use zenoh;   // 利用側と版ズレを起こさせない
```

**代償を明示する**: これで zenoh が reiny の**公開依存**になり、zenoh のメジャー更新が
reiny の破壊的変更になる。それでも、liveliness / queryable / attachment を
「reiny が用意するまで待つ」よりは遥かに安い。README に一行で書く ——
*ここから先は zenoh の semver があなたのものになる*。

この 1 本があることで、以降の §2.3〜§2.7 は「無いと詰む機能」ではなく
「毎回書かせるには大きすぎる定型」に格下げされる。優先度判断はその前提で行った。

### 2.3 presence —— `publish` に liveliness を同伴させる（最優先）

`Cloudy::publish::<T>()` が、zenoh Publisher と**同じキーの LivelinessToken を同時に宣言**し、
`Publisher<T>` がそれを保持する。`Publisher` が drop されればトークンも落ち、購読側に
離脱が届く。

```rust
impl Cloudy {
    /// 現在この型を publish している grain id のスナップショット（自分を含む）。
    pub async fn publishers<T: Topic>(&self) -> Result<Vec<String>>;
    /// 参加 / 離脱イベントのストリーム。
    pub fn watch_publishers<T: Topic>(&self) -> Result<Presence<T>>;
}

pub enum PresenceEvent { Joined(String), Left(String) }
```

実装は zenoh 1.10 の `session.liveliness()`（`zenoh/src/api/session.rs:1274`）配下の
`declare_token` / `declare_subscriber` / `get`（`zenoh/src/api/liveliness.rs:121,157,193`）。
liveliness subscriber の Sample は `SampleKind::Put` = 参加、`Delete` = 離脱なので、
キーから `<id>` 段を取り出すだけで足りる。

**なぜ最優先か。** これは「reiny が奪ったまま返していない機能」である。0.1 系のダウン
ストリームは zenoh liveliness を直接使い、*プロセスが落ちた瞬間に GUI のタブが消える*
という挙動を持っていた。reiny 移行でセッションが閉じたため、同じことを**アプリ層の
ハートビート + タイムアウト**で書き直す羽目になっている（HumanoidSystem
`hs-control-app/src/server/mod.rs:76-78, 758-767` および `server/imu.rs:15`）。
0.3 では次の 2 行になる:

```rust
let live = cloudy.publishers::<WorldState>().await?;
let physics_live = live.iter().any(|id| id != cloudy.id());
```

タイムアウト定数・ハートビート購読・フラッピング対策コメントがまとめて消える。

トークン宣言は **opt-out を設けない**。「presence を持たない publisher」を許すと
`publishers()` の戻り値が信用できなくなり、機能そのものが無意味になる。

### 2.4 送信元を返す

```rust
pub struct Envelope<T> {
    pub value: T,
    pub source: String,                               // キーの <id> 段
    pub timestamp: Option<zenoh::time::Timestamp>,    // zenoh の timestamping 有効時のみ
}

impl<T> Subscriber<T> {
    pub async fn recv(&mut self) -> Option<T>;                  // 0.2 互換。変更なし
    pub async fn recv_envelope(&mut self) -> Option<Envelope<T>>;
}

impl Cloudy {
    pub fn subscriber<T>(&self) -> SubscriberBuilder<T>;  // .from(id) / .latched()
}
```

`Sample::key_expr()` / `timestamp()`（`zenoh/src/api/sample.rs:266,296`）は現状
`recv()` の中で**捨てられているだけ**なので、追加の実行コストはゼロ。

`from(id)` は購読キーを `reiny/<ns>/<id>/<TYPE>` に固定する。同じ型を複数の grain が
publish する構成（例: `WorldState` を制御と物理の両方が出す）で、購読側が出し手を
選べるようになる。

### 2.5 latched pub/sub（遅参者）

```rust
cloudy.publisher::<RobotConfigBundle>().latched().build()?;   // 直近 1 件を保持し問い合わせに答える
cloudy.subscriber::<RobotConfigBundle>().latched().build()?;  // 宣言 → 直近値を get → ライブへ
```

**`zenoh-ext` は入れない。** 実体は次の 2 つで、合計 30 行程度に収まる。

- publish 側: 自分の publish キーに Queryable を 1 本立て、最後に送った値を返す。
- subscribe 側: subscriber を宣言した**直後に** `get()` を 1 回撃ち、その応答を配る。

`zenoh-ext` の `AdvancedPublisher` / `AdvancedSubscriber` は多機能すぎて、依存 1 本と
API 追随の義務に見合わない。

**競合の扱いを設計として固定する**: `get` の応答はライブ sample より遅れて届きうる。
**ある source について既にライブ sample を配ったあとに届いた応答は捨てる**
（latest-wins、n = 1 前提）。履歴 n > 1 は入れない —— 要求が出てから考える。

**何を消すか。** HumanoidSystem は `RobotConfigBundle`（起動時に 1 回で足りる内容）を
**1Hz で再配信し続ける常駐タスク**を持っている（`hs-control-app/src/server/publish.rs:14-38`。
コメントに「後から起動したコンポーネントも受け取れるように」と理由がそのまま書いてある）。
latched はこれを丸ごと消す。

### 2.6 起動まわりの行儀

| 変更          | 中身                                                                       | 現状                            |
| ------------- | -------------------------------------------------------------------------- | ------------------------------- |
| tracing       | `RuntimeOptions.install_tracing`（既定 true）。`#[reiny::main(tracing = false)]` でも指定可 | `lib.rs:304` の `try_init()`    |
| SIGTERM       | unix で `SignalKind::terminate` も shutdown をトリガ                        | `lib.rs:327` は Ctrl+C のみ     |
| 明示 shutdown | `Cloudy::shutdown_now()` を公開（`Shutdown` 自体は `pub(crate)` のまま）    | 外から止める手段なし            |
| 未知引数      | **エラーにしない**。`Cloudy::extra_args()` で残りを渡すだけ                 | `lib.rs:274` で黙って読み飛ばす |
| tokio         | `RuntimeOptions.worker_threads`                                            | `new_multi_thread()` 固定       |

未知引数を**エラーにしない**のは意図的である。grain 固有の引数（`--port` など）は
reiny が知りようがなく、厳格化すると既存の grain が全部落ちる。タイポ検出は grain 側の
引数パーサの仕事であり、reiny にできるのは「残りを渡す」ところまで。

**何を消すか。** `try_init()` は**先に誰かが subscriber を入れていたら黙って何もしない**。
このためダウンストリームの GUI grain は「reiny より先に自前の subscriber を入れる」順序
依存を抱え、`crates/hs-gui/tests/log_capture.rs` という回帰テストで固定している。
`--log-level` の二重パースもこれが原因。`install_tracing = false` で丸ごと不要になる。

### 2.7 スキーマ指紋

```rust
pub trait Topic {
    const TYPE: &'static str;
    /// スキーマ指紋。reiny-build 生成型は descriptor から算出する。
    /// 手書き impl は None のままでよい（既定値付きなので破壊的ではない）。
    const SCHEMA: Option<u64> = None;
}
```

publish 時に attachment へ載せ（`zenoh::sample::SampleBuilderTrait::attachment`、
`zenoh/src/api/builders/publisher.rs:207-212`）、subscribe 時に**両側が `Some` で
不一致なら source ごとに 1 回だけ warn して捨てる**。片方でも `None` なら素通し。

- **既定値付き const なので、既存の手書き `impl Topic` は無改造で通る。** これは
  重要で、reiny の売りの 1 つが「第三者は自分の型に `impl Topic` を手書きするだけで
  参加できる」（`lib.rs:75-78`）である。ここを壊してはいけない。
- `TYPE` が proto パッケージを剥がした素の型名である以上、名前空間は平坦なままで、
  別プロジェクトの同名型が同じトピックに乗りうる。protobuf は寛容なので、
  フィールド番号がたまたま噛み合うと**decode が成功して黙って化ける**。
  指紋はその平坦さに対する唯一の安全弁である。

## 3. ビルド（`reiny-build`）

### 3.1 `[schema]` の多クレート化（本設計の目玉）

**現状の行き止まり**: `[schema]` は 1 マニフェストに 1 個で、しかも `compile_protos` が
`prost_build::Config` を関数内に閉じ込めているため `extern_path` を渡せない
（`reiny-build/src/lib.rs:557-568`）。結果として **スキーマを複数クレートへ分割した瞬間、
reiny-build から降りるしかない**。降りると `impl Topic` の自動生成・`reiny check` の
型→トピック表・トピック衝突検証を全部失う。

0.3 では `[schema]` を複数取れるようにする。

```toml
[schema.geometry]
crate  = "myapp-proto-geometry"
protos = ["proto/geometry/geometry.proto", "proto/geometry/time.proto"]

[schema.state]
crate   = "myapp-proto-state"
protos  = ["proto/state/state.proto"]
depends = ["geometry"]              # Cargo の dep 辺と一致させること

[internals]                          # 0.2 のまま。所属は proto パスから自動で決まる
RobotState = { proto = "proto/state/state.proto", message = "hs.RobotState" }
```

0.2 の `[schema] crate = "..."` 形は**そのまま動く**（要素 1 個の糖衣として扱う）。

**動作**（パッケージ `myapp-proto-state` をビルドしているとき）:

1. 自分の `protos` だけを prost コンパイルする。`file_descriptor_set_path` も出す。
2. `depends` のスキーマが公開している FQN 一覧に対して **`extern_path` を自動生成**する。
   → リーフ型（`Vector3` など）の重複生成がゼロになる。
3. 自分に属する `[internals]` 型にだけ `impl Topic` を生成する。
4. 自分の proto ディレクトリと**自分が定義した FQN 一覧**を、cargo の `links` メタとして出す:

   ```text
   cargo:proto_include=<abs dir>
   cargo:proto_types=hs.Vector3,hs.Quaternion,hs.Pose,...
   ```

   消費側は `DEP_<LINKS>_PROTO_INCLUDE` / `DEP_<LINKS>_PROTO_TYPES` を読む。

**FQN 一覧を descriptor set から取るのが要点である。** proto を正規表現で舐めると
ネスト型で必ず外し、`Reiny.toml` に手で書かせると必ず腐る。ちょうど §2.7 の指紋も
同じ descriptor から算出できるので、両者は 1 回のコンパイルを共有する。

**crates.io で成立するのがこの形の値打ち。** `links` 経由なので、**公開済みのスキーマ
クレートを外部プロジェクトから使っても** include パスと extern リストが解決する
（`Reiny.toml` は公開パッケージに入らないため、これ以外に手が無い）。パッケージには
`include` で `proto/**` を同梱させる必要がある。

唯一の手作業は各スキーマクレートの `Cargo.toml` に `links = "<crate_ident>"` を 1 行
書くこと。reiny-build はこれを書けない（Cargo.toml を書き換える立場に無い）ので、
欠けていたら actionable なエラーで指摘する —— 0.2 で識別子検証をそうしたのと同じ流儀。

**何を消すか。** ダウンストリームで進行中の proto 6 分割は、`links` / `DEP_*` /
`extern_path` / `protoc-bin-vendored` を**手書きした build.rs 6 本（約 120 行）**を
要求していた。0.3 ではその 6 本が `reiny_build::compile()` の 1 行に戻り、
失っていた 3 機能（`impl Topic` 生成・型→トピック表・衝突検証）も戻る。
`reiny check` は所有クレート列を 1 本足すだけで、分割後の地図になる。

### 3.2 prost の逃げ道

```rust
pub fn compile_with(f: impl FnOnce(&mut prost_build::Config)) -> Result<()>;
```

`compile()` は `compile_with(|_| {})` になる。これで開くもの:

- **`type_attribute` で wire 型に serde を derive** —— ダウンストリームの GUI が
  webview へ渡す DTO を手書きしている理由がこれ。
- `file_descriptor_set_path` —— 動的デコード（`prost-reflect`）の道が開く。
  汎用モニタや記録ツールを書くなら必須。reiny 本体に `subscribe_raw` を足す必要が
  無くなるのは、この 1 行のおかげである。
- `bytes()` / `btree_map` / `boxed` など、prost 側の既存ノブ全部。

ついでに `unsafe { env::set_var("PROTOC") }`（`reiny-build/src/lib.rs:548-555`。
build script のプロセスグローバル書き換え）を `Config::protoc_executable()` へ
置き換えて消す。

## 4. 足さないもの（意識的に）

| 却下したもの                                | 理由                                                                                   |
| ------------------------------------------- | -------------------------------------------------------------------------------------- |
| 型付き request/response（queryable ラッパ） | 実消費者がまだ居ない。`session()` で書ける。入れると API 面が倍になる                  |
| `subscribe_raw` / 動的デコード              | §3.2 の `file_descriptor_set_path` で `prost-reflect` が使える。reiny 本体には要らない |
| トピック文字列の上書き / remap              | type=topic を壊す。名前空間（§1）だけが唯一の可変部という線を守る                      |
| `Reiny.toml` への QoS 記述                  | QoS は**配備**の性質であってスキーマの性質ではない。builder（§5）に置く                |
| `[projects.*]` の強制化                     | grain は宣言していないリーフ型を正当に使う。表示用メタのままにし、doc で明言する        |
| 0.2 との wire 互換シム                      | 0.x で既知利用者は 1 つ。互換層の維持費が上回る                                        |
| latched の履歴 n > 1                        | 最新値だけで実需要（config 配布）は満たせる。n > 1 は競合解決が別物になる               |

## 5. 公開 API 差分

```rust
pub use zenoh;

pub trait Topic {
    const TYPE: &'static str;
    const SCHEMA: Option<u64> = None;      // 既定値付き = 既存 impl は非破壊
}

impl Cloudy {
    pub fn domain(&self) -> &str;
    pub fn session(&self) -> &zenoh::Session;
    pub fn shutdown_now(&self);
    pub fn extra_args(&self) -> &[String];

    pub fn publisher<T>(&self)  -> PublisherBuilder<T>;   // .latched() .priority() .congestion() .express()
    pub fn subscriber<T>(&self) -> SubscriberBuilder<T>;  // .from(id) .latched()

    pub async fn publishers<T: Topic>(&self) -> Result<Vec<String>>;
    pub fn watch_publishers<T: Topic>(&self) -> Result<Presence<T>>;
}

impl<T> Subscriber<T> {
    pub async fn recv_envelope(&mut self) -> Option<Envelope<T>>;
}

pub struct Envelope<T> { pub value: T, pub source: String, pub timestamp: Option<zenoh::time::Timestamp> }
pub enum PresenceEvent { Joined(String), Left(String) }
pub struct RuntimeOptions { /* §2.1 */ }
pub fn run_with(opts: RuntimeOptions, user: /* … */) -> Result<()>;

// reiny-build
pub fn compile_with(f: impl FnOnce(&mut prost_build::Config)) -> Result<()>;
```

**`publish::<T>()` / `subscribe::<T>()` / `recv()` はシグネチャも意味も不変。**
0.2 のユーザコードは、キー形式（§1）以外まったく手を入れずに通る。追加分はすべて
builder か新メソッドであり、既存の 1 行 API を太らせない。

### 8.1 入ったもの

### 8.2 設計から変えた点

- **`ZenohSource::Config` は `Box<zenoh::Config>`**。素で持つと enum が肥大して
  `clippy::large_enum_variant` に当たる。
- **`RuntimeOptions.id` / `.domain` は `Option<String>` ではなく `String`**
  (§2.1 の素案は `Option`)。`from_args` / `new` が既定を必ず埋めるので、`Option` は
  「未解決の状態」を型に残すだけだった。
- **`--connect` / `--zenoh-mode` は `RuntimeOptions.zenoh_overrides`** という
  `(key, json5)` 列に落とし、セッション構築後に `Config::insert_json5` する。`ZenohSource` を
  即時解決する形にすると `from_args` が `Result` になり、`ZenohSource::File` の遅延解決と
  二重になるため。
- **launch config は launch 全体の `domain` を先に見る**(§2.1 は `GrainEntry` だけ)。
  domain が違う grain 同士は通信しないので、per-grain 指定だけだと全 grain に同じ行を
  書かせることになる。per-grain の `domain` は override として残した。
- **`reiny run --domain` は足していない。** launch config の `domain` と `REINY_DOMAIN`
  (子プロセスへ継承される)で CI の並列ジョブまで賄えるので、ランナーの引数を
  1 本増やす価値が無かった。
- **`--id` / `--domain` をキーセグメントとして検証する**(設計に無かった)。`*` や `/` が
  入ると黙って別のトピックへ行くだけで、エラーにならない。起動時に弾く。
- **`depends` は推移的に閉じていることを要求する**(§3.1 は「Cargo の dep 辺と一致させること」
  としか書いていなかった)。`c` の proto が `b` を、`b` が `a` を import すると `a` の型も
  `c` の descriptor set に入るので、`c` が `a` を extern しないと二重生成される。cargo は
  **直接依存**にしか `DEP_*` を渡さないので、reiny 側で閉包を要求するしかない。宣言漏れは
  「どの区画を足せばよいか」を名指しするエラーにした。
- **区画の include ディレクトリは proto 群の共通祖先 1 本**。cargo のメタ値は 1 行 1 値なので、
  複数ディレクトリを詰めると区切り文字の選定が要る。共通祖先なら必ず 1 つに決まり、
  descriptor 上のファイル名(= 自分のファイルかどうかの判定)も同じ基準で出せる。
- **指紋は自分のフィールドだけから作る(参照先を再帰しない)**。§2.7 は「descriptor から
  算出する」としか言っていない。指紋が守りたいのは「別プロジェクトの同名型が同じトピックに
  乗る」ケースで、それはトップレベルの形だけで判別できる。リーフの変更まで見たいなら、
  そのリーフ自身がトピック型であるべきである。循環参照の処理も要らなくなる。
  ハッシュは **FNV-1a 64** を自前で持つ —— `DefaultHasher` は Rust の版で値が変わりうる。

### 8.3 前回の誤り(訂正)

初回実装時、**QoS builder(§2.6 表 #6)を「zenoh が setter を `internal` + `unstable`
feature の裏に置いているので割に合わない」として落とした**。これは誤りだった。

zenoh の `#[internal_trait]` マクロは、trait のメソッドを **固有メソッドとしても** 型に
生やす([`zenoh-macros`] の doc に「利用者に trait の import を強いない仕組み」と明記が
ある)。つまり `QoSBuilderTrait` を import せずに `.priority()` / `.congestion_control()` /
`.express()` を呼べる —— feature は 1 枚も要らない。`.attachment()` も同じで、これが無ければ
§2.7 の指紋自体が成立しなかった。**trait を import しようとしたことが、使えないように
見せていた。**

0.3.0 の CHANGELOG と CLAUDE.md にあった「QoS は internal + unstable の裏」という記述は
削除し、CLAUDE.md には逆に「この 2 つの trait を import するな」という注意として書き直した。

### 8.4 多クレート `[schema]` の要点

`[schema.<name>]` の実装で効いている事実は 2 つある。

1. **prost-build は import されたファイルの型も生成する**(`--include_imports` を渡している)。
   つまり `msg.proto` が `geometry.proto` を import すると、放っておけば `Point` は
   msg 側にも生成され、**名前が同じだけの別の Rust 型**が 2 つできる。
2. **`extern_path` で指した型は「生成せず参照だけ差し替える」**(prost-build の
   `append_message` が冒頭で extern を見て return する)。しかも解決はプレフィクス一致で
   効くので、externed 型のネスト型も自動で追随する。

したがって分割の実体は「依存区画が定義した FQN 一覧を、依存する側の `extern_path` に
流し込むこと」に尽きる。その一覧を**どうやって渡すか**が唯一の設計判断で、cargo の
`links` メタ(`DEP_<LINKS>_*`)を選んだ。**crates.io 公開後も成立する**のがこれだけだからである
——公開パッケージに `Reiny.toml` は入らないので、相対パスでも共有マニフェストでも解決できない。

代償は `links = "<パッケージ名>"` を各スキーマクレートの `Cargo.toml` へ手で 1 行書くこと。
reiny-build は Cargo.toml を書き換える立場に無いので、欠けていたら
`CARGO_MANIFEST_LINKS` を見て名指しのエラーで止める(0.2 で識別子検証をそうしたのと同じ流儀)。

型の所属は **proto パス**から決まる。`[internals]` 側に所属を書き足させると、proto を
移動したときに 2 箇所直すことになり、片方を忘れる。どの区画にも属さない proto と、
2 区画が取り合う proto はエラーにする —— 黙って生成から漏れる方が高くつく。

### 8.5 まだ入っていないもの

無し(§7 の段 1〜4 は完了)。§4「足さないもの」は意図的に据え置き。

- `cargo clippy --all-targets --all-features -D warnings` / `cargo test` がワークスペースで通る。
- **`crates/reiny/src/e2e.rs`** —— zenoh セッションを 3 本(`lab` × 2 / `other` × 1)実際に張り、
